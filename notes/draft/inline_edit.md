# DRAFT (not yet citation-checked): Applying LLM-proposed inline code edits reliably: edit formats small local models can emit, hunk matching with a formal acceptance criterion, and transactional safety (atomic replace, backup, syntax validation, rollback, incremental re-indexing) for the programmersRAG C++20 edit applier

This file is the raw research dossier. The checked version is `paper/notes/inline_edit.md` once it exists;
prefer that file when it is present.

## Recommendations

- Edit format: adopt a line-number-free, content-anchored, two-mode format. Mode U (unit rewrite, default for the local quantized model): header with file path and the signature line of one function or top-level declaration, followed by the complete new text of that unit in a plain fenced block. Mode S (search/replace): Aider-style '<<<<<<< SEARCH / ======= / >>>>>>> REPLACE' block with the file path and an optional '@@ <function signature>' scope line borrowed from V4A. Choose S only when the block is shorter in tokens than the unit (AdaEdit rule). Do not use line numbers, line ranges, standard unified-diff hunk headers, or JSON/function-call wrapping of code.
- Constrain only the envelope: use a llama.cpp GBNF grammar for the markers, path line, mode tag and fence structure so every response parses, and leave the code payload unconstrained. Measure pass rate with and without the grammar, because format restrictions are reported to reduce reasoning quality.
- Matching ladder: try byte-exact, then trailing-whitespace-insensitive, then leading-and-trailing-whitespace-insensitive (re-indent the replacement by the indentation delta), then Unicode punctuation/space folding. At the first tier that matches anything, require exactly one match within the scope; otherwise refuse. Never apply the first of several matches.
- Bounded fuzzy tier (off by default, enabled per user setting): accept only if exactly one non-overlapping window is within edit distance k = floor(0.10 * |anchor|) and the runner-up is outside k; start from K_min = 3 non-blank lines (4 for mimalloc, where 3-line windows are ambiguous about 9% of the time), tau = 0.90, delta = 0.20, and tune on the corpus. Generate candidates with the k+1 pieces filter over a per-file line-hash index and verify with Myers O(ND) bounded at D <= 2k. Disable the fuzzy tier for multi-hunk edits, where unguarded fuzzy matching reached 39% silent misapplication.
- Scope every anchor search to the retrieved function when the edit names one: the retrieval stage already knows the byte range of each function, so uniqueness is tested inside that range first and in the whole file second. This removes most ambiguity without longer anchors and avoids the context tax.
- Treat each file's hunks as one all-or-nothing transaction (git apply semantics): resolve every hunk against the same snapshot, reject the whole edit if any hunk fails or if two hunks overlap, and apply hunks bottom-up so earlier offsets stay valid.
- Validate before commit: parse the new content with tree-sitter's C grammar and reject if the count of ERROR or MISSING nodes increases relative to the pre-edit tree (mimalloc's macros may produce baseline error nodes, so compare counts rather than demand zero). Offer an optional stricter gate that runs 'cl /Zs' or 'clang -fsyntax-only' with the project's include paths. On rejection, discard the edit and return the diagnostic plus the before/after snippet to the model, as SWE-agent does.
- Cap automatic retries at 2 per edit and surface the failure to the user afterwards: recovery probability falls from 90.5% to 57.2% after one failed edit, so long retry loops mostly burn tokens.
- Atomic commit on Windows: write the new content to a temporary file in the same directory (same volume), call FlushFileBuffers, re-hash the target and abort if it changed since it was read, then call ReplaceFileW with a backup file name. Handle ERROR_UNABLE_TO_REMOVE_REPLACED (1175), ERROR_UNABLE_TO_MOVE_REPLACEMENT (1176) and ERROR_UNABLE_TO_MOVE_REPLACEMENT_2 (1177) explicitly, restoring from the backup in the 1177 state. For newly created files use MoveFileExW with MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH. On POSIX builds use write, fsync, rename, then fsync of the parent directory.
- Multi-file edits and undo: keep a per-transaction journal that lists each target path, its backup path and its pre-edit hash; flush the journal before the first replace and delete it after the last one so that journal deletion is the commit point; on start-up replay any surviving journal to restore backups. Retain backups for a user-visible undo command.
- Preserve bytes the model did not intend to change: detect and keep each file's line-ending convention and encoding (the mimalloc corpus is LF-only even on Windows), and never normalise whitespace outside the replaced span.
- Incremental re-indexing: key every chunk by a content hash; after a commit, re-parse incrementally with ts_tree_edit and use ts_tree_get_changed_ranges to find affected functions; re-embed only chunks whose hash changed; update the vector index by label update or mark-deleted plus insert; then refresh any density/cluster statistics for those functions. Run this strictly after the commit step so the index never describes uncommitted content.
- Latency: for unit rewrites enable llama.cpp n-gram self-speculative decoding (ngram-simple or ngram-mod), which drafts from text already in the context and needs no second model, an important point with 4 GB of VRAM. Verify the speed-up on the target hardware rather than assuming the cloud figures.
- Fine-tuning data: when the UI toggle is on, log (instruction, retrieved context, emitted edit, apply outcome, validation outcome) for accepted and rejected edits; train the local model on accepted edits in the exact deployed format, choosing per example the shorter of unit rewrite and search/replace. Use format success and apply success as cheap training metrics, as PR-Edit does.
- Evaluation protocol for the paper: follow the known-target design (construct the intended post-edit file first, render the edit in each format, perturb only the location surface with reindentation and line shifts) and report clean success, stress success, clean-failure and silent-misapplication rates separately, with Wilson confidence intervals, on the mimalloc fork. State explicitly that published numbers come from Python/JavaScript/Dart corpora and cloud models, and that Aider, Cursor and hashline figures are non-peer-reviewed.

## Findings

- [established] Plain-text edit formats beat function-call/JSON-wrapped formats. On Aider's 133-exercise Exercism benchmark, 'Using the new functions API for edits performed worse than the above whole file method, for all the models', and the whole-file markdown format was 'the most reliable and effective edit format across all GPT-3.5 and GPT-4 models'. A 2024 follow-up on 4 models found 'LLMs produce lower quality code if they're asked to return it as part of a structured JSON response' and strict JSON mode gave no improvement. These are practitioner benchmarks, not peer-reviewed.  (aider_benchmarks, aider_codejson)
- [established] Aider's line-number-free unified diff raised GPT-4 Turbo (gpt-4-1106-preview) from 20% to 61% on an 89-task Python refactoring benchmark and cut 'lazy comment' tasks from 12 to 4; its four stated design principles are FAMILIAR, SIMPLE (avoid 'brittle specifiers like line numbers or line counts'), HIGH LEVEL (edit whole functions/blocks rather than surgical lines) and FLEXIBLE (tolerant application). Disabling flexible patch application produced a 9X increase in editing errors, and omitting high-level-diff prompting produced a 30-50% increase.  (aider_udiff)
- [established] Location-anchored addressing (line numbers, line ranges, function-by-name) is the most dangerous edit representation. Evidence from four independent sources: Aider ('GPT is terrible at working with source code line numbers'); Cursor ('models are notoriously bad at counting line numbers'); OpenAI's V4A format deliberately omits line numbers; in a controlled apply-step benchmark a one-line shift made line-range edits silently corrupt 99.1% of files and whole-function-by-name edits hit the wrong same-named function 12.7% of the time; and in fine-tuning experiments on Qwen2.5-Coder-7B a line-indexed minimal unified diff reached 14.07% average pass@1 versus 57.07% for full-code output.  (aider_udiff, sanger2024instantapply, openai_gpt41guide, althoubi2026lookbefore, cheng2026todiff)
- [established] The three major vendor/tool formats have converged on content-anchored edits: Aider SEARCH/REPLACE blocks ('<<<<<<< SEARCH / ======= / >>>>>>> REPLACE'), Anthropic's str_replace tool (old_str 'must match exactly, including whitespace and indentation' and must be unique), and OpenAI's V4A apply_patch ('*** Begin Patch / *** Update File: / @@ anchor', 3 lines of context above and below by default, '@@' class/function anchors when 3 lines are not unique; 'we do not use line numbers in this diff format, as the context is enough to uniquely identify code'). OpenAI's guide names SEARCH/REPLACE and pseudo-XML as the other effective formats because they avoid line numbers and provide both the exact code to replace and the replacement with clear delimiters.  (aider_editformats, anthropic_texteditor, openai_gpt41guide, openai_applypatch, codex_applypatch_src)
- [established] Reference appliers disagree on ambiguity policy. Anthropic's documented behaviour refuses both zero matches ('Error: No match found for replacement...') and multiple matches ('Error: Found 3 matches for replacement text. Please provide more context to make a unique match.'). OpenAI Codex's seek_sequence instead returns the first match at or after a cursor, trying four tiers of decreasing strictness (exact; ignore trailing whitespace; ignore leading and trailing whitespace; Unicode punctuation/space normalisation). Aider tries exact, then leading-whitespace-tolerant, then '...' elision matching; its edit-distance fuzzy matcher (difflib SequenceMatcher, threshold 0.8) is present in the source but disabled by an early return.  (anthropic_texteditor, codex_applypatch_src, aider_editblock_src)
- [established] For small local models, whole-unit output is the format they comply with most reliably. On Aider's code-editing leaderboard every Ollama-served local model is benchmarked with the 'whole' format and most reach 97-100% format compliance (qwen2.5-coder:32b 100.0%, qwen2.5-coder:14b 98.5%, qwen2.5-coder:7b-instruct-q8_0 100.0%, Qwen2.5-Coder-0.5B-Instruct 100.0%; outliers granite3-dense:8b 78.9%, opencodeinterpreter:6.7b 91.0%), whereas open-weight models run with the search/replace 'diff' format show lower compliance (Qwen2.5-Coder-32B-Instruct 94.7%, openrouter qwen-2.5-coder-32b-instruct 84.2%, llama-3.3-70b-instruct 88.7%, llama3-70b-8192 73.5%).  (aider_leaderboard)
- [recent] Diff generation ability scales steeply with model size and is poor below about 7B parameters. On Diff-XYZ (1,000 real edits from CommitPackFT), the Qwen2.5-Coder family scored on the Apply task EM 0.00 (0.5B), 0.11 (1.5B), 0.36 (3B), 0.59 (7B), 0.82 (14B), 0.85 (32B); on Diff Generation the 7B model had EM 0.03, apply rate 0.19 and parsing rate 0.70, and the 0.5B model had parsing rate 0.23. The authors conclude search-replace 'performs best for larger models' while 'smaller open models benefit little from any formatting choice'.  (glukhov2025diffxyz)
- [recent] For very small models trained in both regimes, direct whole-file generation beat iterative search/replace editing by about 40-45 percentage points of static-analysis pass rate: Rainbow-Pony-100M 0.802 vs 0.347 and fine-tuned Qwen2.5-Coder-0.5B 0.900 vs 0.501 (about 1,790 held-out Flutter/Dart tasks each). Diff-based editing was competitive only on short, spatially localised edits ('task locality'). Single-author preprint, Dart only.  (andrejev2026diffswhole)
- [contested] Which format is best is model-size dependent and the literature does not agree on a single winner: Agentless reports Search/Replace edits are 'more cost-efficient, but also more reliable and accurate' for strong API models; Diff-XYZ finds search-replace best for large models; Cascaded Code Editing finds whole-file and search/replace competitive with unified diff worst; AdaEdit finds content-addressed diff (54.43 avg pass@1) below full code (57.07) on a fine-tuned 7B model; and small-model studies favour whole-file output.  (xia2024agentless, glukhov2025diffxyz, wang2026cascaded, cheng2026todiff, andrejev2026diffswhole, aider_leaderboard)
- [recent] Structure-aware unit rewrites recover full-code accuracy at lower cost. BlockDiff/FuncDiff represent a change as a rewrite of a syntactically coherent unit (control structure or function) extracted from the AST. On fine-tuned Qwen2.5-Coder-7B, FuncDiff averaged 57.32 and BlockDiff with AdaEdit 57.61 pass@1 versus FullCode 57.07, ContentDiff 54.43, UniDiff 33.15 and MinUniDiff 14.07; AdaEdit 'reduc[es] both latency and cost by over 30% on long-code editing tasks'. The paper attributes diff failures to 'fragile offsets' (line-indexed) and 'fragmented hunks that break the syntactic integrity of code' (content-addressed), and notes unchanged context lines 'often disorient the model'.  (cheng2026todiff)
- [recent] Edit-format competence can be trained into a small local model. GRPO training of Qwen3-8B with an adaptive find-replace/whole-file policy raised format success from 76.8% to 90.4% and downstream edit success from 68.6% to 81.1% (parity with GPT-5-nano as an editor); CanItEdit showed fine-tuned EditCoder models (DeepSeekCoder base) improve instructed-editing pass@1 (EditCoder-33b 55.90% descriptive vs 49.78% for the best open baseline); NextCoder (SeleKT adaptation of QwenCoder-2.5) reports gains on five code-editing benchmarks while retaining generation ability.  (zhang2026sweedit, cassano2023canitedit, aggarwal2025nextcoder)
- [recent] Search/replace and unified diff pay a 'Context Tax': because the old code is the search anchor, 'models generate extensive surrounding context to disambiguate similar or repeated code patterns', which 'negates theoretical efficiency gains'. A two-stage cascade (large model writes a sketch, a small fine-tuned Qwen2.5-Coder 0.5B-14B model applies it) reached Pass@2 75.1 with DeepSeek-R1 + Qwen2.5-Coder-14B versus 67.6 direct on Aider Polyglot.  (wang2026cascaded)
- [established] Fast-apply systems rewrite the file and recover speed by speculation on the unchanged text. Cursor's fine-tuned Llama-3-70b apply model reached about 1000 tokens/s (about 3500 char/s), a ~13x speedup over vanilla inference, using 'speculative edits' which 'speculate on future tokens using a deterministic algorithm rather than a draft model' and are 'equivalent to a full-file-rewrite, while being up to 9x faster'. Cursor lists three reasons diffs are hard for models: fewer output tokens to think in, diffs being out of distribution, and line-number output. OpenAI Predicted Outputs exposes the same idea through a 'prediction' parameter. The underlying technique, speculative decoding, provably leaves the output distribution unchanged (2X-3X on T5-XXL).  (sanger2024instantapply, fireworks2024cursor, openai_predicted, leviathan2023speculative)
- [recent] A draft-model-free local equivalent exists: llama.cpp's server implements n-gram self-speculative decoding (ngram-simple, ngram-map-k, ngram-mod; e.g. '--spec-type ngram-simple --spec-draft-n-max 64'), and its documentation gives 'the rewriting of source code by a LLM' as the example use. PLD+ reports that tuning-free input-copy speculation is effective for input-guided tasks including code editing.  (llamacpp_speculative, somasundaram2024pldplus)
- [established] Grammar-constrained decoding can guarantee that a local model's output follows a required structure without fine-tuning; llama.cpp implements this as GBNF ('a format for defining formal grammars to constrain model outputs'), so the envelope of an edit block (markers, path line, fences) can be made syntactically unbreakable.  (geng2023gcd, llamacpp_gbnf)
- [contested] Constraining format has a cost: 'we observe a significant decline in LLMs reasoning abilities under format restrictions' and 'stricter format constraints generally lead to greater performance degradation in reasoning tasks'; Aider likewise found code inside JSON 'more prone to syntax errors'. Whether a light envelope-only grammar harms small code models is not measured in any source opened here.  (tam2024speakfreely, aider_codejson)
- [established] A syntax guard on the edit tool measurably improves task success. In SWE-agent's ACI ablation on SWE-bench Lite with GPT-4 Turbo, editing with linting resolved 18.0% versus 15.0% without linting and 10.3% with no edit command; 'Invalid edits are discarded, and the agent is asked to try editing the file again'. Failed edits cascade: 1185 of 2942 trajectories (51.7%) had at least one failed edit, and the chance of an edit eventually succeeding dropped from 90.5% to 57.2% after a single failed edit.  (yang2024sweagent)
- [recent] Content-anchored formats fail cleanly while location-anchored formats fail silently. In an apply-only benchmark (640 edits over 224 Python files, 23,040 trials with reindentation and line-shift perturbations, known target file), stress success / silent-failure rates were: exact search/replace 0.176 / 0.000; whitespace-normalised 0.571 / 0.000; fuzzy 0.977 / 0.023; unified diff via GNU patch 0.375-0.536 / 0.000; line range 0.000 / 0.991; whole function 0.000 / 0.127. Single-author preprint, Python only, synthetic perturbations.  (althoubi2026lookbefore)
- [recent] Safety is a property of the applier policy as well as the format: a permissive first-match policy raised silent misapplication of content-anchored edits from 0.000 to 0.020 (exact) and 0.023 (whitespace-normalised). Independently, in small-model search/replace trajectories where ambiguous search spans were resolved by a first-occurrence heuristic, pass rates were 0.123 (100M model) and 0.175 (Qwen2.5-Coder-0.5B) versus 0.570 and 0.800 without fallback; fallback-affected trajectories accounted for roughly 65-71% of failures among normally completed runs.  (althoubi2026lookbefore, andrejev2026diffswhole)
- [recent] A refuse-when-unsure applier (Robust-Apply) that requires a minimum anchor size, a unique exact or whitespace-normalised match, or else a fuzzy match above a similarity floor that beats the runner-up by a margin, with (K_min, tau_hi, delta) = (2, 0.90, 0.20), recorded one silent misapplication in 8,320 trials (0.01%); across tau_hi in [0.85, 0.95] and delta in [0.10, 0.30] the silent rate stayed at or below 0.05%. The cost is applicability (0.51 versus 0.98 on perturbed single-hunk edits). Unguarded fuzzy matching on multi-hunk edits reached a 39% silent rate. The similarity function is not specified in the paper.  (althoubi2026lookbefore)
- [established] Classical patch tools already encode the accuracy/safety trade-off. GNU patch scans forward and backward from the expected line and, with fuzz factor f (default 2), ignores the first and last f context lines; its manual warns 'a larger fuzz factor increases the odds of making a faulty patch' and that 'results are guaranteed only when the patch is applied to an exact copy of the file that the patch was generated from'. git apply ignores no context by default, discourages context-free patches, and 'for atomicity ... by default fails the whole patch and does not touch the working tree when some of the hunks do not apply'.  (gnu_patch_inexact, git_apply_docs, gnu_unified_format)
- [established] diff-match-patch applies patches by fuzzy location using the Bitap algorithm and a score that adds normalised error count and normalised distance from the expected location (defaults Match_Threshold 0.5, Match_Distance 1000, Patch_DeleteThreshold 0.5, Patch_Margin 4, Match_MaxBits 32). Fraser's design note argues GNU patch's strategy is 'unrestricted by location' and that context length must be tailored per edit until the block is unique in the file.  (dmp_src, dmp_api, fraser2006fuzzypatch)
- [established] Myers' algorithm finds a shortest edit script in O(ND) time by greedy furthest-reaching D-paths on the edit graph, with expected time O(N + D^2) and a linear-space divide-and-conquer refinement via the middle snake; LCS length L and script length D are dual (D = N + M - 2L). It 'performs well when differences are small', which is the regime of verifying a near-match between a model-quoted block and a file window.  (myers1986ond)
- [established] Patience diff anchors on lines that occur exactly once on both sides and takes the longest common subsequence of those; histogram diff extends it 'to support low-occurrence common elements' by choosing the lowest-occurrence common element as split point and runs in O(N*D) when the chain length cap is a small constant (64). An empirical study found that for code changes Histogram is more suitable than Myers and recommends it. Git's default remains Myers.  (cohen2010patience, jgit_histogram, git_diff_docs, nugroho2019diff)
- [established] Approximate string matching theory supplies the primitives for a bounded-error matcher: edit distance is a metric (symmetric, satisfies the triangle inequality); searching pattern P of length m in text T with at most k errors is the dynamic program with first row set to zero, reporting positions where C_m <= k in O(mn) time and O(m) space; the error level is alpha = k/m; the matching probability is very low and exponentially decreasing in m below a critical error level and rises sharply to almost 1 above it; Wu-Manber's bit-parallel (bitap/agrep) algorithm handles k errors with two shifts, one AND and three ORs per error level per text character.  (navarro2001guided, wu1992agrep)
- [established] Pigeonhole filtering: 'if a pattern is cut in k+1 pieces, then at least one of the pieces must appear unchanged in an approximate occurrence', so candidate locations can be found by exact search of the pieces and verified only in a neighbourhood of length m + 2k. Wu and Manber state the same partition approach.  (navarro2001guided, wu1992agrep)
- [established] Uniqueness of an anchor is what makes independent edits compose safely. For diff3, a configuration whose untouched separating region contains an element occurring exactly once in each of O, A and B always yields a unique conflict-free merge (Theorem 4.1.1), whereas separation by a long or merely distinct region does not; idempotence, stability and near-success do not hold in general.  (khanna2007diff3)
- [established] Source code is highly repetitive at short anchor lengths. Fraser measured that in the Linux kernel source 'a fifteen-character pattern is likely to occur 250 times in the same file' (largely decorative comment lines), against under 2% repeat probability in English prose.  (fraser2006fuzzypatch)
- [our_proposal] Local measurement on the evaluation corpus (mimalloc clone, 59 .c/.h files, 31,174 lines, LF line endings only, largest file src/arena.c 2,777 lines / 117 KB, 31 of 59 files under 400 lines): the fraction of k-line windows that are NOT unique within their own file after whitespace trimming is 45.2% (k=1), 21.6% (k=2), 9.4% (k=3), 4.1% (k=4), 2.0% (k=5). So the conventional 3 lines of context leaves roughly 1 window in 11 ambiguous, which motivates a uniqueness check plus a function-scope anchor rather than a fixed context size.  (local_mimalloc_measurement)
- [established] POSIX requires rename to be atomic with respect to visibility: if the link named by new exists 'it shall be removed and old renamed to new' and 'a link named new shall remain visible to other threads throughout the renaming operation and refer either to the file referred to by new or old before the operation began'. Linux documents the same ('there is no point at which another process attempting to access newpath will find it missing') and that rename fails with EXDEV across mount points. Durability is separate: fsync of the file 'does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed.'  (posix_rename, linux_rename_man, linux_fsync_man)
- [established] On Windows, Microsoft recommends write-new-then-replace for document-like files: 'A common approach is to write the document to a new file, then replace the original file with the new one. One method to do this is with the ReplaceFile API.' ReplaceFileW takes an optional backup file name, preserves creation time, short name, object identifier, DACLs, encryption, compression and named streams of the replaced file, and requires that 'the backup file, replaced file, and replacement file must all reside on the same volume'. MoveFileExW offers MOVEFILE_REPLACE_EXISTING and MOVEFILE_WRITE_THROUGH ('does not return until the file is actually moved on the disk'). FlushFileBuffers writes buffered data to the device and requires GENERIC_WRITE.  (ms_txf_alternatives, ms_replacefilew, ms_movefileexw, ms_flushfilebuffers)
- [established] The Windows API reference pages for ReplaceFileW and MoveFileExW do not state an atomicity guarantee. ReplaceFileW documents three partial-failure states (ERROR_UNABLE_TO_REMOVE_REPLACED 1175, ERROR_UNABLE_TO_MOVE_REPLACEMENT 1176, ERROR_UNABLE_TO_MOVE_REPLACEMENT_2 1177), in one of which the replaced file survives only under the backup name, and REPLACEFILE_WRITE_THROUGH is 'not supported'. Ordinary renames fail if the target has open handles; FILE_RENAME_POSIX_SEMANTICS (FileRenameInformationEx, Windows 10 RS1 and later) allows 'replacing a file even if there are existing handles to it'. An applier must therefore treat these error codes explicitly rather than assume all-or-nothing behaviour.  (ms_replacefilew, ms_movefileexw, ms_file_rename_info)
- [established] Crash consistency of the write-temp-then-rename idiom depends on file-system behaviour: across six Linux file systems 'persistence properties vary widely', directory operations such as rename 'are seemingly atomic on all file systems that use techniques like journaling or copy-on-write', and the append-then-rename idiom is specially recognised by several file systems; the ALICE study found 60 crash vulnerabilities in 11 widely used applications. SQLite shows the journal-based alternative for multi-file atomicity: write original content to a rollback journal, flush it, modify, flush, and treat deletion of the journal (or of the super-journal for multi-file transactions) as the commit point, with hot-journal replay on recovery.  (pillai2014crash, sqlite_atomiccommit)
- [established] Syntax validation before commit is available at two cost levels. Tree-sitter is designed to be 'fast enough to parse on every keystroke' and 'robust enough to provide useful results even in the presence of syntax errors'; its C API exposes ts_node_has_error, ts_node_is_error and ts_node_is_missing, incremental re-parse after ts_tree_edit (the new tree 'internally shares structure with the old tree') and ts_tree_get_changed_ranges. Compilers offer a full front-end check without code generation: clang -fsyntax-only ('Run the preprocessor, parser and semantic analysis stages') and MSVC /Zs ('check only the syntax ... no output files are created').  (treesitter_intro, treesitter_advanced, treesitter_api, clang_cli, msvc_zs)
- [recent] Incremental re-indexing after an edit is established practice in components but thinly evaluated end to end. A 2026 coding-agent paper describes an index 'updated incrementally on subsequent runs via Merkle-tree diffs over the working copy, so a source edit invalidates and re-indexes only the affected chunks', built from tree-sitter parses into vector, call-graph and BM25 indices, but states the incremental path was 'not load-bearing' in its evaluation. AST-based chunking (cAST) improves Recall@5 by 4.3 points on RepoEval. hnswlib supports incremental insertion, in-place update of an existing label, and mark_deleted with optional slot reuse; FreshDiskANN shows graph ANN indices can absorb real-time inserts and deletes while retaining >95% 5-recall@5.  (bhola2026codeisntmemory, zhang2025cast, hnswlib_readme, singh2021freshdiskann, treesitter_api)
- [established] Code-editing benchmarks are Python-centric and none opened here targets C. SWE-bench has 2,294 tasks from 12 Python repositories; CanItEdit has 105 hand-written Python problems (210 with two instruction styles) and models output the entire 'after' code; EDIT-Bench (ICLR 2026) has 540 in-the-wild problems in Python and JavaScript where only 1 of 40 models exceeds 60%; Diff-XYZ covers Python, JavaScript, Java, Kotlin and Rust; CodeEditorBench evaluates 19 LLMs on debugging, translating, polishing and requirement switching. An audit found CanItEdit and EDIT-Bench 'concentrate over 90% of evaluation on Python'. Results must therefore be re-measured on the mimalloc C corpus rather than assumed to transfer.  (jimenez2023swebench, cassano2023canitedit, chi2025editbench, glukhov2025diffxyz, guo2024codeeditorbench, ebrahimi2026editverify)
- [contested] A non-peer-reviewed harness study ('hashline': each line shown to the model carries a short content hash that edits must cite, so stale references are rejected) reports, over 16 models and 3 runs of 180 mutation-repair tasks, that the V4A-style patch format was worst for nearly every model not trained on it (patch failure rate 50.7% for Grok 4, 46.2% for GLM-4.7) and that hashline matched or beat str_replace for most models. It is a vendor blog on React/JavaScript files and should be treated as a hypothesis to test, not an established result.  (boluk2026harness)
- [our_proposal] OUR PROPOSAL (format): use a two-mode, line-number-free, content-anchored format. Mode U (default for the local <=8B quantized model): whole-unit rewrite, where the model re-emits one complete function or top-level declaration identified by file path plus the unit's signature line, and the applier replaces the tree-sitter node whose text the retrieval stage supplied. Mode S: a SEARCH/REPLACE block for edits much smaller than the unit. Mode is chosen by token length as in AdaEdit. Only the envelope (markers, path, mode tag) is grammar-constrained; code is emitted as plain fenced text, never inside JSON. Rationale: small models comply with whole-output formats at about 100% but not with diffs; unit rewrites match full-code accuracy; plain text beats JSON; envelope grammars remove parse failures.  (aider_leaderboard, glukhov2025diffxyz, andrejev2026diffswhole, cheng2026todiff, aider_benchmarks, aider_codejson, llamacpp_gbnf, geng2023gcd, zhang2026sweedit)
- [our_proposal] OUR PROPOSAL (acceptance criterion): accept an edit only if (1) the anchor has at least K_min non-blank lines, and (2) at the first normalisation tier that yields any match (bytes; trailing whitespace; leading whitespace; Unicode punctuation) the match is unique in the file or in the named unit, or else (3) exactly one non-overlapping window lies within edit distance k = floor(alpha*|S|) of the anchor and the runner-up lies outside it. Otherwise refuse with a structured error naming the candidates. Soundness: if the intended target is within k of the quoted anchor, an accepted match is necessarily the intended target; by the triangle inequality the rule never refuses for ambiguity when all other windows differ from the target by more than 2k. Never use first-match. Suggested starting values K_min = 3-4 lines, alpha = 0.10, which corresponds to the similarity floor 0.90 validated empirically by Robust-Apply.  (navarro2001guided, althoubi2026lookbefore, andrejev2026diffswhole, anthropic_texteditor, codex_applypatch_src, local_mimalloc_measurement)
- [our_proposal] OUR PROPOSAL (transaction protocol): READ (record content hash h0) -> MATCH (criterion above, all hunks of a file or none) -> BUILD new content in memory preserving the file's line-ending convention -> VALIDATE (tree-sitter error/missing-node count must not increase; optional cl /Zs or clang -fsyntax-only) -> STAGE (write temp file in the same directory, flush) -> GUARD (re-hash target, abort if it differs from h0) -> COMMIT (ReplaceFileW with backup name on Windows; rename plus directory fsync on POSIX) -> JOURNAL (multi-file edits listed in a journal whose deletion is the commit point) -> REINDEX (only chunks whose content hash changed). Rollback restores from the backup; the index update is ordered strictly after commit.  (ms_replacefilew, ms_txf_alternatives, posix_rename, linux_fsync_man, sqlite_atomiccommit, git_apply_docs, yang2024sweagent, treesitter_api, msvc_zs, clang_cli, bhola2026codeisntmemory, boluk2026harness)

## Formulas

### Edit (Levenshtein) distance recurrence

$$
C_{i,0}=i,\quad C_{0,j}=j,\quad C_{i,j}=\begin{cases} C_{i-1,j-1} & \text{if } x_i=y_j \\ 1+\min\{C_{i-1,j},\,C_{i,j-1},\,C_{i-1,j-1}\} & \text{otherwise}\end{cases},\qquad ed(x,y)=C_{|x|,|y|}
$$

Taken from Navarro (2001), Sec. 5.1.1. C_{i,j} is the minimum number of insertions, deletions and replacements turning x_{1..i} into y_{1..j}. Time O(|x||y|), space O(min(|x|,|y|)). Navarro also states that ed is symmetric, ed(x,x)=0 and ed(x,z) <= ed(x,y)+ed(y,z), so strings form a metric space; this triangle inequality is what the acceptance-criterion proposition below relies on.

Sources: navarro2001guided

### Approximate search with at most k errors

$$
C_{0,j}=0\ \ \forall j\in\{0,\dots,n\};\qquad \text{report } j \iff C_{m,j}\le k \iff \exists i:\ d(P,T_{i..j})\le k
$$

Taken from Navarro (2001), Sec. 3 (problem statement) and Sec. 5.1.2: the same dynamic program with the first row set to zero lets a match start at any text position; 'the text positions where C_m <= k are reported'. Search time O(mn), space O(m). In the applier, P is the model-quoted anchor and T is the file (or the named function).

Sources: navarro2001guided

### Error level

$$
\alpha = k/m,\qquad 0<\alpha<1
$$

Navarro (2001), Sec. 3: the fraction of the pattern allowed to be wrong. Navarro's Sec. 4 shows the probability that a random pattern matches a text position is exponentially decreasing in m for low alpha and rises sharply to almost 1 beyond a critical error level that depends on alphabet size, which is why a bounded-error matcher must keep alpha small and the anchor long. (Symbols in that section were partly lost in the PDF text layer, so only the qualitative statement is used here.)

Sources: navarro2001guided

### Pigeonhole (k+1 pieces) filter

$$
P=P_1P_2\cdots P_{k+1}\ \wedge\ ed(P,W)\le k\ \Longrightarrow\ \exists\, j\in\{1,\dots,k+1\}:\ P_j \text{ occurs unchanged in } W
$$

Navarro (2001), Sec. 8: 'if a pattern is cut in k+1 pieces, then at least one of the pieces must appear unchanged in an approximate occurrence. This is evident, since k errors cannot alter the k+1 pieces.' Candidates are then verified in a neighbourhood of length m+2k. Wu and Manber (1992) give the same partition approach. Generalisation in Navarro: cutting into j pieces guarantees one piece appears with at most floor(k/j) errors.

Sources: navarro2001guided, wu1992agrep

### Wu-Manber bit-parallel transition for d errors (bitap / agrep)

$$
R^{0}_{j+1}=\mathrm{Rshift}[R^{0}_{j}]\ \mathrm{AND}\ S_c,\qquad R^{d}_{j+1}=\big(\mathrm{Rshift}[R^{d}_{j}]\ \mathrm{AND}\ S_c\big)\ \mathrm{OR}\ \mathrm{Rshift}[R^{d-1}_{j}]\ \mathrm{OR}\ \mathrm{Rshift}[R^{d-1}_{j+1}]\ \mathrm{OR}\ R^{d-1}_{j},\qquad c=t_{j+1},\ \ R^{d}_{0}=1^{d}0^{m-d}
$$

Eq. (2.1) of Wu and Manber (1992), transcribed from an OCR'd scan, so notation is normalised. R^d is an m-bit vector whose i-th bit says the first i pattern characters match a suffix of the text read so far with at most d errors; S_c marks the pattern positions holding character c. The four terms are match, substitution, deletion and insertion: 'a total of two shifts, one AND, and three ORs for each R^d'. Running time is O(nk*ceil(m/w)) for word size w, effectively O(nk) when the pattern fits in a machine word.

Sources: wu1992agrep, navarro2001guided

### Myers LCS / shortest-edit-script duality and diagonal lemma

$$
D = N + M - 2L;\qquad \text{a } D\text{-path ends on diagonal } k=x-y\in\{-D,\,-D+2,\,\dots,\,D-2,\,D\};\qquad T_{worst}=O((N+M)D),\ \ T_{expected}=O(N+M+D^{2})
$$

Myers (1986), Sec. 2-4, with |A|=N, |B|=M, L the LCS length and D the number of inserted plus deleted symbols in a shortest edit script. Lemma 1 gives the diagonal parity used by the greedy algorithm, which stores only the furthest-reaching x per diagonal in array V. A linear-space refinement finds the middle snake by running forward and reverse searches until they overlap (Lemma 3).

Sources: myers1986ond

### Relation between Levenshtein and insert/delete-only distance (our derivation)

$$
ed(x,y)\ \le\ d_{LCS}(x,y)=|x|+|y|-2L\ \le\ 2\,ed(x,y)
$$

Own derivation, status our_proposal. Left inequality: every insert/delete script is also a Levenshtein script. Right inequality: replace each substitution in an optimal Levenshtein script by one deletion plus one insertion, at most doubling the cost. Consequence: a Myers O(ND) verifier can certify ed <= k by exploring only D <= 2k, costing O((|S|+|W|)*2k) per candidate window, and can reject as soon as D exceeds 2k.

Sources: myers1986ond, navarro2001guided

### diff-match-patch match score

$$
s(e,x)=\frac{e}{|P|}+\frac{|x-\mathrm{loc}|}{\mathrm{Match\_Distance}},\qquad \text{valid match iff } s\le \mathrm{Match\_Threshold}
$$

From the diff-match-patch C++ source (match_bitapScore: accuracy = e / pattern.length(); proximity = |loc - x|; return accuracy + proximity / Match_Distance) and the API wiki. e is the error count of the Bitap match at position x, loc the expected location. Defaults: Match_Threshold 0.5, Match_Distance 1000. These defaults are permissive (up to half the pattern wrong) and the library picks the best-scoring match without a uniqueness test, so they are unsuitable as-is for unattended code edits.

Sources: dmp_src, dmp_api

### Fraser's fuzzy-patch score

$$
s=\frac{e/p}{c}+\frac{d/t}{1-c}
$$

Fraser (2006): e = number of errors (Levenshtein distance), p = pattern length, d = offset in characters from the expected location, t = text length, c = constant weighting accuracy against distance. Lower is better. Fraser notes the function must never have a reverse correlation between score and distance or errors.

Sources: fraser2006fuzzypatch

### Robust-Apply acceptance rule (anchor-and-verify)

$$
\text{apply}\iff |A|\ge K_{\min}\ \wedge\ \Big(\exists!\,m\ \text{(exact or whitespace-normalised match of } A \text{ in } F)\ \ \vee\ \ \big(s_1\ge\tau_{hi}\ \wedge\ s_1-s_2\ge\delta\big)\Big),\qquad (K_{\min},\tau_{hi},\delta)=(2,\,0.90,\,0.20)
$$

Algorithm 1 of Althoubi (2026). A is the anchor, (m_1,s_1),(m_2,s_2) are the top-2 fuzzy matches by similarity; otherwise return Clean-Fail ('ambiguous; refuse rather than guess'). Reported outcome: one silent misapplication in 8,320 trials (0.01%); silent rate at or below 0.05% over tau_hi in [0.85,0.95], delta in [0.10,0.30]; applicability 0.51 versus 0.98 for unguarded fuzzy on perturbed single-hunk edits. The similarity function is not named in the paper.

Sources: althoubi2026lookbefore

### Proposed tiered uniqueness criterion (exact tiers)

$$
\mathcal{M}_t=\{\,i:\ \nu_t(f_{i+j-1})=\nu_t(s_j)\ \ \forall j=1..m\,\},\qquad t^{*}=\min\{t:\mathcal{M}_t\neq\emptyset\},\qquad \mathrm{ACCEPT}_{exact}\iff m\ge K_{\min}\ \wedge\ |\mathcal{M}_{t^{*}}|=1
$$

Own proposal. F=(f_1..f_n) are the file's lines (or the lines of the named function), S=(s_1..s_m) the quoted anchor lines, and nu_0..nu_3 the normalisers identity, strip trailing whitespace, strip leading and trailing whitespace, and Unicode punctuation/space folding (the four tiers implemented by OpenAI Codex's seek_sequence). Unlike Codex, which returns the first hit, the rule demands exactly one hit at the strictest tier that matches anything, following Anthropic's uniqueness rule and Althoubi's finding that first-match raises silent misapplication from 0.000 to about 0.02. When nu_2 is the accepting tier, the replacement text is re-indented by the indentation delta between anchor and file, as Aider does.

Sources: codex_applypatch_src, anthropic_texteditor, althoubi2026lookbefore, aider_editblock_src

### Proposed bounded-error criterion and soundness proposition (fuzzy tier)

$$
d_{(1)}\le k<d_{(2)},\quad k=\lfloor\alpha\,|S|\rfloor;\qquad \big[\,ed(S,W^{*})\le k\ \wedge\ d_{(1)}\le k<d_{(2)}\,\big]\Rightarrow W_{(1)}=W^{*};\qquad \big[\,\forall W\neq W^{*}:\ ed(W^{*},W)>2k\,\big]\Rightarrow ed(S,W)\ \ge\ ed(W^{*},W)-ed(S,W^{*})\ >\ k
$$

Own derivation. d_(1) and d_(2) are the smallest and second-smallest edit distances between the anchor S and mutually non-overlapping candidate windows of the file; W* is the window the model intended. Soundness: suppose ed(S,W*) <= k and the rule accepts. If the selected window W_(1) were not W*, then W* would be a second window within distance k, giving d_(2) <= k, contradicting k < d_(2). Completeness condition: by the triangle inequality for edit distance, if every other window differs from W* by more than 2k, no other window can be within k of S, so the rule never refuses for ambiguity. This is the unique-decoding-radius argument of coding theory applied to anchors: the file's windows act as codewords with minimum distance greater than 2k. Candidates are generated with the k+1 pieces filter and verified with a banded or O(ND) computation.

Sources: navarro2001guided, althoubi2026lookbefore, myers1986ond

### Similarity floor expressed as an error level

$$
\sigma(S,W)=1-\frac{ed(S,W)}{\max(|S|,|W|)}\ \ge\ \tau\iff ed(S,W)\le(1-\tau)\max(|S|,|W|)
$$

Own definition, chosen so that thresholds are interpretable in the metric used by the proposition above. With tau = 0.90 the admitted error level is alpha = 0.10, the operating point Robust-Apply validated empirically. It differs from Aider's disabled fallback, which uses Python difflib's SequenceMatcher ratio with threshold 0.8, and from Robust-Apply, whose similarity function is unspecified; thresholds are therefore not directly transferable between tools and must be re-tuned on the target corpus.

Sources: althoubi2026lookbefore, aider_editblock_src, navarro2001guided

### AdaEdit format-selection rule

$$
E_j=\arg\min_{S\in\{C'_j,\ \mathrm{Diff}(C_j,C'_j)\}}|S|
$$

Eq. (3) of Cheng et al. (2026): for each training pair of source code C_j and target C'_j the ground-truth output is whichever of the full target code or the diff representation has fewer tokens under the model's tokenizer; the model internalises the switch during fine-tuning. We reuse it at the unit level: emit a SEARCH/REPLACE block when it is shorter than re-emitting the enclosing function, otherwise re-emit the function.

Sources: cheng2026todiff

### Empirical anchor-ambiguity curve on the mimalloc corpus

$$
A(k)=\Pr[\text{a } k\text{-line window is not unique within its file}],\qquad A(1..5)=0.452,\ 0.216,\ 0.094,\ 0.041,\ 0.020\ \approx\ 0.452\cdot 0.46^{\,k-1}
$$

Own measurement and fit, status our_proposal. Computed over all 59 .c/.h files of the local mimalloc clone with lines whitespace-trimmed and windows counted within each file. The geometric ratio 0.46 is the fourth root of 0.0202/0.452. Reading: to keep expected ambiguity under 5% an anchor needs at least 4 lines; the conventional 3 lines leaves about 9%. It is a corpus statistic, not a guarantee, which is why uniqueness is tested at apply time instead of assumed.

Sources: local_mimalloc_measurement, fraser2006fuzzypatch

### Atomic-replace and rollback invariants

$$
\forall t:\ \mathrm{content}_t(\pi)\in\{C_{old},\,C_{new}\}\qquad\wedge\qquad \big(\mathrm{state}_t\neq\mathrm{COMMITTED}\ \Rightarrow\ \exists\,\beta:\ \mathrm{content}_t(\beta)=C_{old}\big)\qquad\wedge\qquad \big(\mathrm{COMMIT}\ \text{only if}\ H(\mathrm{content}(\pi))=h_0\big)
$$

Own formalisation. pi is the target path, beta the backup path, h_0 the hash recorded when the file was read for matching. The first conjunct is what POSIX rename guarantees for observers ('a link named new shall remain visible ... and refer either to the file referred to by new or old'). On Windows it is the documented intent of ReplaceFileW but not a stated guarantee: error 1176 without a backup name leaves no file under pi and error 1177 leaves the original only under the backup name, so the second conjunct (always pass lpBackupFileName) is what makes recovery possible. The third conjunct is an optimistic-concurrency guard against edits computed on a stale snapshot.

Sources: posix_rename, ms_replacefilew, ms_txf_alternatives, boluk2026harness

## Open questions

- No opened benchmark measures edit emission or edit application on C code; every quantitative result cited comes from Python, JavaScript, Dart or mixed Java/Kotlin/Rust corpora. How do format compliance, apply success and silent-misapplication rates change on mimalloc-style C with heavy macro use and conditional compilation?
- How does 4-bit (or custom) quantization of a 3B-8B local model affect exact reproduction of anchor text? None of the opened sources reports edit-format compliance as a function of quantization level, and the Aider leaderboard rows mix q4, q8 and fp16 builds without a controlled comparison.
- Which similarity function and thresholds are right for C? Robust-Apply does not name its similarity measure, Aider's disabled fallback uses difflib ratio at 0.8, diff-match-patch defaults to 0.5, and our proposal uses normalised Levenshtein at 0.90. The thresholds are not comparable across measures and need calibration on the target corpus.
- Is the tree-sitter C grammar a reliable validity gate for mimalloc? Macro-heavy code can yield ERROR or MISSING nodes in unmodified files, so the proposed rule compares error counts before and after; the false-accept and false-reject rates of that rule are unmeasured, as is the latency of a full 'cl /Zs' check per edit with the project's include paths.
- What does Windows actually guarantee under power loss? The ReplaceFileW and MoveFileExW reference pages do not state atomicity or durability, REPLACEFILE_WRITE_THROUGH is documented as unsupported, and the crash-consistency study opened here covers Linux file systems only. NTFS behaviour under crash, and interference from antivirus or indexer handles on the target file, need direct testing.
- Does an envelope-only GBNF grammar reduce code quality for small models? The evidence that format restrictions harm reasoning concerns JSON/XML-style constraints on general tasks, and the evidence that JSON wrapping harms code concerns cloud models; neither isolates a light marker-only grammar on a local code model.
- Is hash-anchored line addressing (hashline) better than content anchors for small local models? The only evidence is a vendor blog on JavaScript files with cloud models; it conflicts in spirit with findings that location-anchored edits fail silently, although the hash check converts stale references into clean failures. A controlled comparison under the known-target protocol is missing.
- How large is the real 'context tax' on this corpus: for typical mimalloc edits, how many tokens does a unique search anchor cost relative to re-emitting the enclosing function, and at what function length does search/replace become cheaper given about 9% ambiguity at 3 lines of context?
- How should the edit applier and the retrieval index be kept consistent under concurrency: if a query is answered while an edit is being committed, which snapshot does retrieval see, and does the project's strict block-ordering guarantee extend to the commit-then-reindex sequence?
- Does fine-tuning on the project's own accepted edits improve apply success without degrading general code generation? SWE-Edit and NextCoder report gains with GRPO and SeleKT on cloud-scale training sets; whether a few hundred locally logged edits are enough, and whether they cause overfitting to one repository, is unknown.
