## Recommendations

- Make the block size a run-time parameter with a default of 16 KB, and derive its ceiling at start-up from the machine: read every L1 data cache entry through GetLogicalProcessorInformationEx (CACHE_RELATIONSHIP: Level, CacheSize, LineSize, Associativity, and the processor mask that shares it) and set B_max = min over core types of CacheSize / (2 * logical processors sharing). On the i9-12950HX this yields min(32 KB / 2, 48 KB / (2*... )) and keeps 16 KB inside Intel's 'one quarter to one half' window for both core types.
- Budget the whole working set, not only the input block: input (16 KB) + per-block output + scratch + hot stack must fit 32 KB on an E-core and about 24 KB on a P-core logical CPU with a busy SMT sibling. Keep per-block outputs compact (e.g. int8-quantised vectors and offsets, not float32 copies of the text) and reuse one thread-local scratch arena for every block.
- Process each block in several passes (strip-mining / multi-pass execution: split into functions, tokenise, hash or embed, quantise, score) before moving to the next block. The L1 benefit exists only when the same lines are touched repeatedly; a single streaming pass gains nothing from L1 sizing.
- Store block data in contiguous, 64-byte aligned buffers and access it sequentially so the L1 next-line/IP-stride prefetchers and L2 streamer can work; cut blocks at function boundaries nearest to the 16 KB target rather than at arbitrary byte offsets, and allow an oversized function to form its own block.
- Prevent false sharing: put the dispatch counter, the commit cursor and each worker's state on separate cache lines with alignas(64) (or std::hardware_destructive_interference_size; Intel even suggests 128-byte separation for synchronisation variables). Workers write only thread-local memory until commit.
- Dispatch blocks dynamically at run time with a single atomic ticket (morsel style), never by static equal partitioning, because P-cores and E-cores differ in speed. Do not hard-pin threads with SetThreadAffinityMask; if placement must be steered use the CPU Sets API, and make the worker count configurable (test 8, 16 and 24) instead of assuming hardware_concurrency is optimal.
- Implement ordering with the ticket + ring-buffer protocol: CAS-claimed sequence numbers, a ring of K result slots (start with K = 2 to 4 times the worker count), back-pressure when next - committed reaches K, and a commit cursor that advances only in sequence. Keep both serial stages tiny: the dispatcher only hands out a (pointer, length, sequence) triple and the commit only appends a pointer or memcpy of a small result.
- Avoid long busy-waiting at the commit gate on this hybrid CPU: spin briefly with PAUSE, then block on a condition variable or std::atomic::wait, or use a 'drain' variant in which any finishing worker commits all consecutive completed slots under a try-lock and re-checks after releasing it.
- Select the int8 dot-product kernel by CPUID at run time: AVX-VNNI VPDPBUSD (256-bit) when available, otherwise AVX2 VPMADDUBSW + VPMADDWD + VPADDD with inputs restricted so the 16-bit pair sums cannot saturate (for example 7-bit magnitudes), otherwise scalar. Handle signed embeddings with the +128 offset correction. Do not use AVX-512 on this machine.
- In the research paper, state the claims precisely: (a) 'the per-thread working set is sized to fit the L1 data cache (16 KB block, at most C/h total)'; not 'the computer is forced to use L1'; (b) 'block i's start event precedes block i+1's start event and results commit in sequence order'; not 'block A physically reaches the CPU first'. Give the invariants and the induction proof, and state the assumptions (pure per-block function, terminating computation, eventual scheduling).
- Validate experimentally and report honestly: sweep block size (4 KB, 8 KB, 16 KB, 32 KB, 64 KB, 256 KB, 1 MB) and thread count, separately on P-cores only, E-cores only and all cores; report time per byte, speed-up and, where a profiler such as VTune or Windows Performance Recorder is available, L1D miss/replacement counters. Report a negative or flat result if 16 KB is not better than L2-sized blocks.
- Add a determinism test to the test suite: run indexing of the mimalloc demo corpus with 1, 2, 8, 16 and 24 threads and several block sizes and require byte-identical committed output, plus a stress test that injects random delays into workers to exercise out-of-order completion.
- Use the speed-up bounds to set expectations: measure d, w and c per block, compute s = (d+c)/(d+w+c) and P_eff from measured per-core throughput, and compare the measured speed-up with min(P_eff, (d+w+c)/max(d,c)) and with the Amdahl value. With only about 80 blocks in the corpus, also report absolute times, since start-up and I/O may dominate.

## Findings

- [established] Cache blocking (tiling) is the classical technique: instead of operating on whole rows/columns, blocked algorithms operate on sub-blocks 'so that data loaded into the faster levels of the memory hierarchy are reused'. Intel's current optimization manual still recommends the same family of transformations (strip-mining for 1-D arrays, loop blocking for 2-D) and says each chunk 'should be small enough to fit all the data for a given computation into the cache, thereby maximizing data reuse'.  (lam1991blocked, intel2024optmanual)
- [established] Lam, Rothberg and Wolf showed that block size must not simply equal the cache size: 'The conventional wisdom of trying to use the entire cache, or even a fixed fraction of the cache, is incorrect'. In their direct-mapped model, choosing the block to use the entire cache gave a miss rate 'more than 10 times the optimal', and the best fixed block used only 3%-15% of the cache because of self-interference (conflict) misses. With 4-way set associativity the average miss rates 'remain relatively flat as the block size increases' because the critical blocking factors become much larger. Their analysis is for 2-D matrix blocks accessed at non-unit stride, not for contiguous 1-D buffers.  (lam1991blocked)
- [established] Intel's official sizing rules: (a) User/Source Coding Rule 8: 'Optimize data structures either to fit in one-half of the first-level cache or in the second-level cache', and 'Optimizing for one-half of the first-level cache will bring the greatest performance benefit in terms of cycle-cost per data access', while optimizing for a point in between (e.g. the entire L1) 'will likely not bring a substantial improvement over optimizing for the second-level cache'. (b) User/Source Coding Rule 25: 'Use cache blocking to improve locality of data access. Target one quarter to one half of the cache size when targeting Intel processors supporting HT Technology'. (c) The upper limit of the block size is 'the total size of the cache divided by the number of logical processors serviced by that cache'.  (intel2024optmanual)
- [established] Official cache geometry of the target CPU family (12th Gen Core, datasheet covers the HX line): P-core L1 is 48 KB data + 32 KB instruction, 12-way; E-core L1 is 32 KB data + 64 KB instruction, 8-way; L2 is 1.25 MB per P-core and 2 MB shared by 4 E-cores; L1 caches are not shared between physical cores. For Gracemont the Intel manual gives a typical 4-cycle L1 load-to-use latency and an L2 latency of 17 cycles whose bandwidth 'is shared among four cores'.  (intel2025adl_datasheet, intel2024optmanual)
- [established] Two logical processors of one SMT (Hyper-Threading) core share the L1 data cache: Intel states that 'Most resources in a physical processor are fully shared ... including caches and all the execution units', and Drepper measured that with two hyper-threads 'each thread has only half the cache and bandwidth available'. Hence a P-core logical CPU has an effective L1d share of about 24 KB when its sibling is busy, while an E-core (no SMT) has the full 32 KB.  (intel2024optmanual, drepper2007memory, intel2025adl_datasheet)
- [our_proposal] OUR ANALYSIS of the 16 KB choice: 16 KB is exactly one-half of the E-core L1d (32 KB) and one-third of the P-core L1d (48 KB), i.e. two-thirds of a P-core logical CPU's 24 KB share under SMT. Intel's 'one quarter to one half' window is 8-16 KB for E-cores and 12-24 KB for P-cores, so the intersection valid for every core type is 12-16 KB and 16 KB is the largest block size that satisfies Intel's rule on both core types. Geometry: both L1d caches have 64 sets (32768/(8*64) = 49152/(12*64) = 64), so set index + line offset use 12 address bits, the 4 KB page offset; a virtually contiguous 16 KB buffer (256 lines) therefore occupies exactly 4 ways in every set (4 of 8 on E-cores, 4 of 12 on P-cores) and cannot conflict with itself. Consequence: an input block plus an equally large output block would already fill all 8 ways of an E-core L1d, so the rule must be applied to the whole working set (input + output + scratch + stack), not to the input block alone.  (intel2025adl_datasheet, intel2024optmanual)
- [established] Vectorised query execution is the database precedent for cache-sized work units. MonetDB/X100 passes 'small, cache-resident, vertical data fragments called vectors' between operators; default vector size is 1024 and 'all vectors together should comfortably fit the CPU cache size'. In its TPC-H Q1 experiment the optimum was about 1000 tuples, 'all values between 128 and 8K actually work well', and 'Performance starts to deteriorate when intermediate results do not fit in the cache anymore'; with vector size 1 interpretation overhead dominates. Kersten et al. (2018) reproduced this: 'small (<64) and large vector sizes (>64 K) decrease performance significantly ... Large vectors do not fit into the CPU caches and therefore cause cache misses'.  (boncz2005x100, kersten2018compiledvectorized)
- [established] Morsel-driven parallelism separates the scheduling unit from the cache unit: work is handed out at run time in 'morsels' (about 100,000 tuples) by a lock-free dispatcher executed by the requesting worker itself, with work stealing. It reports 'an average speedup of over 30 with 32 cores'. With an unrelated process occupying one core, static partitioning lost 36.8% performance versus 4.7% with dynamic morsel assignment. The authors cache-line align each thread's local range so that 'conflicts at the cache line level are unlikely'. A 2025 paper still calls it 'the state of the art morsel-driven parallelism'.  (leis2014morsel, chakraborty2025recursive)
- [contested] CONTESTED: whether sizing blocks to L1 (rather than L2) matters. Leis et al. state 'there is no performance penalty if a morsel does not fit into cache ... the morsel size is not very critical for performance, it only needs to be large enough to amortize scheduling overhead'; X100 ran well for any vector set fitting L1+L2 (up to 8K tuples x 40 bytes = 320 KB); Drepper notes 'If data is only needed once this obviously is not necessary since the cache would be ineffective anyway'. Against that, Intel states that optimizing for one-half of L1 'will bring the greatest performance benefit in terms of cycle-cost per data access'. The reconciliation is that L1-sized blocks only pay off when each block is touched several times (multi-pass processing or reused per-thread scratch); for a single streaming pass, hardware prefetching makes L1 residency largely irrelevant.  (leis2014morsel, boncz2005x100, drepper2007memory, intel2024optmanual)
- [established] Measured working-set effect: Drepper's sequential-walk experiment on a CPU with a 16 kB L1d and 1 MB L2 shows 'three distinct levels' (up to 2^14 bytes, 2^15-2^20 bytes, 2^21 and up): about 4 cycles per element while the working set fits L1d, about 9 cycles once it spills to L2 (less than the 14-cycle L2 latency because of prefetching), and with effective prefetching about 9 cycles instead of 200+ for main memory. The edges are not sharp 'because the caches are used by other parts of the system as well and so the cache is not exclusively available for the program data'.  (drepper2007memory)
- [established] Sequential scans are the best case for both theory and hardware. In the ideal-cache/external-memory model, scanning N contiguous elements costs at most ceil(N/B)+1 block transfers. Intel advises 'Try to arrange data structures so they permit sequential access' because 'the automatic hardware prefetcher can prefetch data'; 'The prefetcher can recognize up to eight concurrent streams'. Gracemont has 'three independent L1 prefetchers' (next-line on L1 load misses, IP-based stride, next-page). L2 streamer/DPL prefetchers 'prefetch only inside page boundary (4 KBytes)'.  (demaine2002cacheoblivious, intel2024optmanual, drepper2007memory)
- [established] Cache-oblivious algorithms are the alternative to parameter tuning: Frigo et al. give algorithms in which 'no variables dependent on hardware parameters, such as cache size and cache-line length, need to be tuned to achieve optimality', analysed in the ideal-cache model with cache size Z and line length L under the tall-cache assumption Z = Omega(L^2); an optimal cache-oblivious algorithm for two levels is optimal for multiple levels. This matters on a hybrid CPU where L1d differs between core types (48 KB vs 32 KB): a fixed 16 KB block is a cache-aware choice that must be re-tuned on other hardware.  (frigo1999cacheoblivious, demaine2002cacheoblivious, intel2025adl_datasheet)
- [established] What user-space code CANNOT guarantee about cache placement: (1) there is no instruction that places or pins data in a given cache level; PREFETCH 'merely provides a hint to the hardware' and 'the cache level [is] specified as a hint'; (2) 'As for the cache replacement there is not much a programmer can do', and for physically addressed caches it is 'impossible for user-level processes' to control set mapping; (3) the cache is shared with the OS, other processes and an SMT sibling; (4) Windows schedules threads pre-emptively in round-robin time slices and a higher-priority thread pre-empts immediately, so a thread can lose the CPU (and its warm L1) at any point; (5) affinity only restricts where a thread may run ('In most cases, it is better to let the system select an available processor'), and CPU Sets are explicitly 'soft'. What user space CAN do: query the real L1d size, line size and associativity (CACHE_RELATIONSHIP via GetLogicalProcessorInformationEx, or CPUID deterministic cache parameters), bound the working set, keep accesses sequential, align data, and verify with performance counters. The owner's phrase 'force the computer to use L1 cache' must therefore be stated as: the per-thread working set is sized so that it can reside in L1d; residency is an expected, measurable outcome, not a guarantee.  (intel2024optmanual, drepper2007memory, msdocs_scheduling, msdocs_affinity, msdocs_cpusets, msdocs_cache_relationship, intel2021hybridwp)
- [established] False sharing: 'False sharing occurs when processors in a shared-memory parallel system make references to different data objects within the same coherence block (cache line or page), thereby inducing unnecessary coherence operations'. Intel: 'Beware of false sharing within a cache line (64 bytes)' and 'Place each synchronization variable alone, separated by 128 bytes or in a separate cache line'. C++17 provides std::hardware_destructive_interference_size ('Minimum offset between two objects to avoid false sharing') for alignas. The Disruptor paper and the morsel paper both apply this to their sequence counters / per-thread ranges.  (bolosky1993falsesharing, intel2024optmanual, bastien2016p0154, cppreference_interference, thompson2011disruptor, leis2014morsel)
- [established] SIMD int8 dot products: VPDPBUSD 'is an 8-bit integer multiply-accumulate vector operation into a vector of 32-bit integer accumulators' that replaces the three-instruction sequence VPMADDUBSW + VPMADDWD + VPADDD 'with higher accuracy' because the older sequence saturates 16-bit intermediates. It exists in VEX-encoded 128/256-bit form under the AVX-VNNI CPUID flag; the Alder Lake datasheet lists 'Intel AVX2 Vector Neural Network Instructions (Intel AVX2 VNNI)' and the Intel manual lists 'VEX-based VNNI ISA extension' for Gracemont, so both core types support it. One operand is unsigned bytes and the other signed bytes, so signed-by-signed products need an offset correction. On E-cores most 256-bit uops are split into two 128-bit uops, and Alder Lake E-cores have no AVX-512, so the portable target is 256-bit AVX2/AVX-VNNI with run-time dispatch.  (intel2024optmanual, intel2025adl_datasheet, intelsdm_vpdpbusd_mirror, intelsdm_pmaddubsw_mirror, kuffo2025bang, velugoti2026hybrid)
- [recent] SIMD speed-ups depend on cache residency. Kersten et al.: 'With a growing working set, gains from SIMD diminish and the execution costs are dominated by memory latency. SIMD is only beneficial when all data fits into the cache.' Recent vector-search work agrees: the PDX kernel 'processes each float in 0.1 CPU cycles when the data fits in L1d' and 'When data size exceeds L2, all kernels become data access-bound'; a 2025 cross-CPU study finds vector search 'is memory-bound in many scenarios' and performance drops 'as soon as data spills to L3'; VSAG (VLDB 2025) attributes production gains to reducing cache misses 'with pre-fetching and cache-friendly vector organization' plus scalar quantization.  (kersten2018compiledvectorized, kuffo2025pdx, kuffo2025bang, zhong2025vsag)
- [established] Ordered parallel pipelines are a standard, documented pattern. In oneTBB a serial_in_order filter 'processes items one at a time. The order in which items are processed is implicitly set by the first serial_in_order filter and respected by all other such filters in the pipeline'; if an item arrives out of order 'the pipeline automatically delays invoking [the output filter] on the item until its predecessors are processed'. A token limit bounds memory: 'Once this limit is reached, the pipeline never creates a new token at the input filter until another token is destroyed at the output filter'. Throughput 'is limited by the throughput of the slowest sequential filter', and for window (block) size 'A good guideline is to try for a large window size that still fits in cache'.  (onetbb_userguide_pipeline, onetbb_userguide_throughput, oneapi_spec_filter_mode)
- [established] The LMAX Disruptor uses sequence numbers as its only coordination mechanism: producers claim the next slot in sequence (a plain counter for one producer, CAS for several) and commit in order by waiting until the cursor equals claimedSequence-1 and then setting cursor = claimedSequence. With one producer 'no locks or CAS operations are required'. Reported mean latency for a three-stage pipeline is 3 orders of magnitude lower than an equivalent queue-based approach and throughput about 8 times higher.  (thompson2011disruptor)
- [established] FIFO admission by ticket: a ticket lock 'consists of two counters, one containing the number of requests to acquire the lock, and the other the number of times the lock has been released'; a processor takes a ticket by fetch-and-increment and waits until its ticket equals the release counter, which 'ensure[s] FIFO service' and 'eliminates the possibility of starvation'. Caveat from the same paper: the FIFO guarantee 'is likely to waste CPU resources if spinning processes may be preempted', which applies to any strictly ordered gate on a pre-emptive desktop OS.  (mellorcrummey1991scalable)
- [established] Ordered commit after out-of-order completion is the reorder-buffer principle of processors: 'Instructions are allowed to finish out of order, but a special buffer called the reorder buffer is used to reorder them before they modify the process state'; it is a circular buffer with head and tail pointers whose entry is allocated at issue time and whose results are written only when the entry reaches the head. The simplest scheme that forces in-order completion cost at least 16% performance in their simulation, the better schemes as little as 3%.  (smith1988precise)
- [established] Deterministic multithreading shows that a deterministic order can be imposed on parallel code at modest cost. Kendo enforces 'a deterministic interleaving of lock acquisitions' using deterministic logical clocks (weak determinism) with a geometric-mean overhead of 16% on 4 processors. CoreDet observes that if units 'commit according to the serial scheduling order, the resulting parallel execution is exactly equivalent to the (deterministic) serial execution' and uses parallel and serial modes with a deterministic commit protocol. DThreads isolates threads and commits their updates in an order enforced by a single global token, which 'guarantees a global order for all operations in the serial phase' and also eliminates false sharing.  (olszewski2009kendo, bergan2010coredet, liu2011dthreads)
- [recent] A modern analytical engine uses the same idea at block granularity: DuckDB's order-preserving parallelism has pipeline sources emit a 'batch index'; each thread processes its data in order and the result is reconstructed by scanning 'all the data in the result ordered by batch index', without an extra sort. The PR reports 0.53 s single-threaded versus 0.07 s with 8 threads on a 100M-row example.  (duckdb2022orderpreserving)
- [established] Speed-up laws: Amdahl's 1967 paper (which contains no equation) argues that the sequential housekeeping fraction bounds throughput; Gustafson writes the law as Speedup = 1/(s + p/N) and contrasts it with the scaled speed-up N + (1-N)s' that applies when problem size grows with processor count. Hill and Marty extend Amdahl's law to asymmetric multicores (one large core plus base cores), showing asymmetric chips 'can offer potential speedups that are much greater than symmetric multicore chips (and never worse)' and calling for research on 'the scheduling and overhead challenges that Amdahl's model doesn't capture'.  (amdahl1967validity, gustafson1988reevaluating, hill2008amdahl)
- [recent] Hybrid-core evidence: a 2026 study on Alder Lake (8 P-cores with SMT, 8 E-cores without) found that with thread binding scaling improves up to 8 threads and worsens from 10 to 16 because threads land 'on E-cores which are only 60% the speed of P-cores', and that 'parallel applications with work imbalance ... scale better across hybrid cores when thread affinity is disabled'; the hybrid cache layout had 'very little impact'. Intel's hybrid white paper says 'In general, software should avoid setting affinity', recommends the CPU Sets API if affinity is required, warns that 'Thread creation based on processor count may not always be optimal', and advises replacing active spin-waits with PAUSE/TPAUSE/UMWAIT. Microsoft documents CPU Sets as affinity declared 'in a soft manner that is compatible with OS power management'.  (velugoti2026hybrid, intel2021hybridwp, msdocs_cpusets)
- [our_proposal] OUR MODEL (cost of a block): for a block of B bytes read sequentially in k passes with line size L, first-touch misses are at most ceil(B/L)+1 (257 for 16 KB). If the working set W fits the effective L1d capacity, later passes are L1 hits, otherwise every pass re-misses, so misses are about (B/L)*k. With per-line hit cost t1 and effective miss penalty Delta, the slowdown of an out-of-L1 block relative to an in-L1 block is R(k) = (t1 + Delta)/(t1 + Delta/k), which is 1 for k = 1 and tends to 1 + Delta/t1 for large k. Using Intel's Gracemont latencies (L1 4 cycles, L2 17 cycles) the latency-bound ceiling is 17/4 = 4.25; for prefetched sequential access Drepper's measured 4 vs 9 cycles implies a ceiling nearer 2.25. Real gains are smaller when computation, not memory access, dominates.  (demaine2002cacheoblivious, intel2024optmanual, drepper2007memory)
- [our_proposal] OUR MODEL (speed-up with ordered dispatch and ordered commit): let each block need serial dispatch time d, parallel work w and serial commit time c. Sequential time is N(d+w+c). Because dispatch and commit are each serial, T_P >= max(N*d, N*c, N(d+w+c)/P_eff), so S <= min(P_eff, (d+w+c)/max(d,c)); the pessimistic Amdahl form with serial fraction s = (d+c)/(d+w+c) gives S >= about 1/(s + (1-s)/P_eff) when serial phases cannot overlap anything. For heterogeneous cores P_eff is the sum of relative core speeds; with 8 P-cores at 1.0 and 8 E-cores at 0.6 (SMT ignored) P_eff = 12.8, not 16 or 24. Static equal partitioning finishes when the slowest core finishes, so dynamic per-block dispatch is faster by the factor P_eff/(P*rho_min) = 12.8/(16*0.6) = 1.33 under this model.  (gustafson1988reevaluating, hill2008amdahl, onetbb_userguide_throughput, velugoti2026hybrid, leis2014morsel)
- [our_proposal] OUR PROTOCOL (provably ordered start and commit). Shared state: atomic counters next (dispatch ticket) and committed (commit cursor), each on its own cache line, and a ring of K result slots. A worker claims block i by a compare-and-swap that advances next from i to i+1 only while i - committed < K; processes block i as a pure function of that block into thread-local memory; then waits until committed == i, appends its result, and stores committed = i+1. SAFETY: (1) modifications of one atomic object occur in a single total order, so every ticket value is obtained by exactly one worker and START(i), defined as the successful claim, precedes START(i+1); (2) the commit action for i is enabled only when committed == i, only the unique holder of ticket i can execute it, and it is the only action that changes committed from i to i+1, so by induction commits happen exactly once each in the order 0,1,2,...; the release-store/acquire-load of committed makes COMMIT(i) happen-before COMMIT(i+1). LIVENESS: the holder of the smallest uncommitted ticket is never blocked by the commit guard or by back-pressure, and every wait is on a strictly smaller sequence number, so the wait-for relation is acyclic and, if every block computation terminates and threads are eventually scheduled, all N blocks commit. BOUNDED MEMORY: next - committed <= K always. DETERMINISM: because blocks are pure functions and commits follow serial order, the output equals that of the sequential program for any thread count or schedule.  (mellorcrummey1991scalable, thompson2011disruptor, smith1988precise, onetbb_userguide_pipeline, bergan2010coredet, cppreference_memory_order)
- [our_proposal] OUR PRECISE READING of requirement 9 ('block A must always reach the CPU before block B'): following Lamport, a specification 'must be given in terms of events observable within the system', not physical time. User-space code can guarantee an order on defined events (ticket claim, optional start-gate prologue, commit) but cannot guarantee that the first payload instruction of block A physically executes before that of block B, because the OS may pre-empt the worker of A immediately after its start event. If a stronger observable property is required, a start gate (worker i waits for started == i, performs its prologue such as the first touch of the block, then stores started = i+1) guarantees PROLOGUE(i) happens-before PROLOGUE(i+1), at the cost of adding the prologue to the serial fraction and inheriting the pre-emption sensitivity of FIFO locks. Only full serialization gives a physical ordering of all payload instructions.  (lamport1978time, msdocs_scheduling, mellorcrummey1991scalable, cppreference_memory_order)
- [our_proposal] OUR SCALE CHECK for the evaluation corpus: about 1.3 MB of source splits into roughly 80 blocks of 16 KB, i.e. only 3-4 blocks per logical CPU on a 24-thread machine, and the whole corpus is about the size of one P-core's 1.25 MB L2. Per-block coordination cost and serial stages (file reading, in-order commit) will therefore bound the achievable speed-up; oneTBB's own text-processing example 'has relatively poor speedup, because the serial filters are limited by the I/O speed' and is 'unlikely to see a speedup much more than 2'. Reported speed-ups must be measured, with a block-size sweep, rather than assumed.  (onetbb_userguide_throughput, intel2025adl_datasheet, leis2014morsel)

## Formulas

### Amdahl's law (fixed problem size)

$$
S(N) = \frac{s + p}{s + p/N} = \frac{1}{s + p/N}, \qquad s + p = 1
$$

s = serial time fraction, p = parallelisable fraction, N = processors. Taken verbatim from Gustafson (1988), who states the law in this form; Amdahl's original 1967 paper contains no equation, only the argument that sequential 'data management housekeeping' bounds throughput. Maximum speed-up is 1/s.

Sources: gustafson1988reevaluating, amdahl1967validity

### Gustafson-Barsis scaled speed-up

$$
S_{\text{scaled}}(N) = \frac{s' + p' N}{s' + p'} = N + (1 - N)\, s', \qquad s' + p' = 1
$$

s' and p' are serial and parallel time fractions measured on the parallel system; applies when the problem grows with N (e.g. indexing a larger repository on more cores). From Gustafson (1988).

Sources: gustafson1988reevaluating

### Hill-Marty speed-up, symmetric and asymmetric multicore

$$
S_{\text{sym}}(f,n,r) = \frac{1}{\dfrac{1-f}{\mathrm{perf}(r)} + \dfrac{f\, r}{\mathrm{perf}(r)\, n}}, \qquad S_{\text{asym}}(f,n,r) = \frac{1}{\dfrac{1-f}{\mathrm{perf}(r)} + \dfrac{f}{\mathrm{perf}(r) + n - r}}
$$

f = parallelisable fraction, n = chip budget in base-core equivalents (BCE), r = BCEs spent on the large core, perf(r) = its sequential performance (the paper's graphs assume sqrt(r)). In the asymmetric chip the serial part runs on the large core and the parallel part uses the large core plus n-r base cores. From Hill and Marty (2008).

Sources: hill2008amdahl

### Heterogeneous-core Amdahl bound for P/E hybrids (our generalisation)

$$
S = \frac{1}{\dfrac{s}{\rho_{\text{ser}}} + \dfrac{1-s}{P_{\text{eff}}}}, \qquad P_{\text{eff}} = \sum_{i=1}^{P} \rho_i
$$

OUR DERIVATION, generalising the Hill-Marty asymmetric formula (there the denominator of the parallel term is perf(r)+n-r, i.e. the sum of core performances). rho_i is the speed of core i relative to a P-core and rho_ser the speed of the core running the serial part. With 8 P-cores (rho=1) and 8 E-cores (rho=0.6, the figure reported by Velugoti et al.; must be re-measured) and SMT ignored, P_eff = 8 + 4.8 = 12.8. Example: s = 0.05 on a P-core gives S = 1/(0.05 + 0.95/12.8) = 8.05.

Sources: hill2008amdahl, velugoti2026hybrid

### Speed-up bounds for a pipeline with serial ordered dispatch and serial ordered commit (ours)

$$
T_1 = N(d + w + c), \quad T_P \ge \max\!\Big(N d,\; N c,\; \frac{N(d+w+c)}{P_{\text{eff}}}\Big) \;\Rightarrow\; S = \frac{T_1}{T_P} \le \min\!\Big(P_{\text{eff}},\; \frac{d + w + c}{\max(d, c)}\Big); \qquad S_{\text{Amdahl}} = \frac{1}{s + (1-s)/P_{\text{eff}}},\; s = \frac{d + c}{d + w + c}
$$

OUR DERIVATION. N blocks; d = serial dispatch time per block, w = parallel work per block, c = serial in-order commit time per block. The lower bound on T_P holds because each serial stage must process all N blocks one at a time and total work cannot be done faster than with P_eff cores; this formalises oneTBB's statement that pipeline throughput 'is limited by the throughput of the slowest sequential filter'. The Amdahl form is the pessimistic case where serial phases cannot overlap with parallel work; the true speed-up lies between the two. Example: d = c = 1 microsecond, w = 200 microseconds gives s = 0.0099, upper bound min(P_eff, 202), Amdahl value at P_eff = 12.8 of 11.5.

Sources: gustafson1988reevaluating, onetbb_userguide_throughput

### Dynamic versus static block assignment on heterogeneous cores (ours)

$$
T_{\text{static}} = \frac{N w}{P\, \rho_{\min}}, \qquad T_{\text{dyn}} \approx \frac{N w}{\sum_i \rho_i}, \qquad \frac{T_{\text{static}}}{T_{\text{dyn}}} = \frac{\sum_i \rho_i}{P\, \rho_{\min}}
$$

OUR DERIVATION. With static partitioning each of P threads gets N/P blocks and completion is determined by the slowest core (speed rho_min); with run-time dispatch each core takes blocks in proportion to its speed. For 8 cores at 1.0 and 8 at 0.6 the ratio is 12.8/(16*0.6) = 1.33. Consistent with the morsel paper's measurement (36.8% loss for static vs 4.7% for dynamic under interference) and with the 2026 hybrid study.

Sources: leis2014morsel, velugoti2026hybrid

### Scanning bound in the ideal-cache / external-memory model

$$
Q_{\text{scan}}(N) \le \left\lceil \frac{N}{B} \right\rceil + 1
$$

Number of block (cache-line) transfers to scan N contiguous elements with block size B, for any alignment. Demaine (2002), Theorem 1. Note: the ceiling brackets are not present in the extracted PDF text and were reconstructed from the proof, which counts at most floor(N/B) full blocks plus two partial ones. For a 16 KB block and 64-byte lines this gives at most 257 first-touch line fetches.

Sources: demaine2002cacheoblivious

### Cache-oblivious bounds (ideal-cache model)

$$
Z = \Omega(L^2); \quad Q_{\text{transpose}}(m,n) = \Theta\!\left(1 + \frac{mn}{L}\right); \quad Q_{\text{sort}}(n) = \Theta\!\left(1 + \frac{n}{L}\left(1 + \log_Z n\right)\right); \quad Q_{\text{matmul}} = \Theta\!\left(1 + \frac{mn + np + mp}{L} + \frac{mnp}{L\sqrt{Z}}\right)
$$

Z = cache size, L = cache-line length, tall-cache assumption Z = Omega(L^2). From the abstract of Frigo, Leiserson, Prokop and Ramachandran (FOCS 1999). These bounds hold without tuning any hardware parameter.

Sources: frigo1999cacheoblivious

### Intel block-size rule, formalised

$$
B_{\max} = \frac{C}{h}, \qquad \frac{C}{4} \le B \le \frac{C}{2}
$$

C = size of the target cache, h = number of logical processors served by that cache. The symbols are ours; the content is Intel's: the upper limit of the block size is 'the total size of the cache divided by the number of logical processors serviced by that cache', and Rule 25 says 'Target one quarter to one half of the cache size'. For L1d: E-core C = 32 KB gives 8-16 KB; P-core C = 48 KB gives 12-24 KB; intersection 12-16 KB.

Sources: intel2024optmanual, intel2025adl_datasheet

### L1d set geometry and ways occupied by a contiguous block (ours)

$$
S = \frac{C}{A\, L}, \qquad \text{ways}(B) = \left\lceil \frac{B}{L\, S} \right\rceil
$$

OUR DERIVATION from datasheet numbers. C = cache size, A = associativity, L = 64-byte line. E-core: S = 32768/(8*64) = 64 sets; P-core: S = 49152/(12*64) = 64 sets. Since L*S = 4096 bytes equals the page size, the set index lies within the page offset, so a virtually contiguous block maps uniformly over the sets regardless of physical page placement. A 16 KB block occupies ceil(16384/4096) = 4 ways per set: 4 of 8 on E-cores, 4 of 12 on P-cores.

Sources: intel2025adl_datasheet, intel2024optmanual

### Working-set condition for L1d residency (ours)

$$
W = B_{\text{in}} + B_{\text{out}} + B_{\text{scratch}} + B_{\text{stack}} \le \frac{C_{L1d}}{h}
$$

OUR FORMULATION of the constraint the design must satisfy; h = 2 on a P-core whose SMT sibling is busy, h = 1 on an E-core. With B_in = 16 KB this leaves 16 KB (E-core) or 8 KB (P-core logical CPU under SMT) for everything else. It is a necessary condition for residency, not a guarantee, because the cache is also used by the OS and other code.

Sources: intel2024optmanual, intel2025adl_datasheet, drepper2007memory

### Multi-pass block cost and in-L1 advantage (ours)

$$
T_{\text{block}}(k) = \frac{B}{L}\Big(k\, t_1 + M\, \Delta\Big), \quad M = \begin{cases} 1 & W \le C_{\text{eff}} \\ k & W > C_{\text{eff}} \end{cases}; \qquad R(k) = \frac{t_1 + \Delta}{t_1 + \Delta / k}, \quad \lim_{k \to \infty} R(k) = 1 + \frac{\Delta}{t_1}
$$

OUR DERIVATION. k = number of passes over the block, t1 = cost of an L1 hit per line, Delta = effective extra cost of fetching a line from L2 (reduced by prefetching and out-of-order overlap), M = number of passes that miss. R(k) is the slowdown of a block that does not fit L1d relative to one that does. R(1) = 1: a single pass gains nothing from L1 sizing. Numeric anchors: Gracemont L1 4 cycles and L2 17 cycles give Delta = 13 and a ceiling of 4.25; Drepper's measured sequential walk (about 4 vs about 9 cycles) gives a ceiling of about 2.25.

Sources: intel2024optmanual, drepper2007memory, demaine2002cacheoblivious

### X100 cache-fit condition for vectors

$$
n_{\text{vec}} \cdot \sum_j w_j \le C \qquad (\text{e.g. } 8\text{K} \times 40\ \text{bytes} \approx 320\ \text{KB})
$$

n_vec = tuples per vector, w_j = width in bytes of each vector used by the query. Our notation for the condition described in the X100 paper: total width of all vectors in TPC-H Q1 'is just over 40 bytes', so vectors larger than 8K exceed the 320 KB combined L1+L2 of the AthlonMP and performance degrades. For programmersRAG the analogue is (functions per block) x (bytes of per-function state) plus the raw text.

Sources: boncz2005x100

### VPDPBUSD semantics (int8 dot-product accumulate)

$$
d_i \leftarrow d_i + \sum_{j=0}^{3} \mathrm{zext}\big(a_{4i+j}\big) \cdot \mathrm{sext}\big(b_{4i+j}\big), \qquad i = 0,\dots,7 \text{ for 256-bit}
$$

a = unsigned 8-bit source, b = signed 8-bit source, d = 32-bit accumulators. One 256-bit instruction performs 32 byte multiplications. The non-saturating form wraps; the pre-VNNI AVX2 sequence VPMADDUBSW + VPMADDWD + VPADDD saturates the 16-bit pair sums. For signed-by-signed embeddings x, y in [-128,127], use (x+128) as the unsigned operand and subtract 128 * sum(y) afterwards (the correction described in Intel's manual for signed activations).

Sources: intelsdm_vpdpbusd_mirror, intelsdm_pmaddubsw_mirror, intel2024optmanual

### Ticket / sequence guards for ordered start and ordered commit (ours, built on the ticket lock and Disruptor)

$$
\textsf{claim}: \; i \leftarrow \textsf{next},\; \text{if } i - \textsf{committed} < K \text{ then } \mathrm{CAS}(\textsf{next}, i, i+1); \qquad \textsf{commit}(i) \text{ enabled} \iff \textsf{committed} = i; \qquad \textsf{commit}(i): \; \text{append } r_i;\; \textsf{committed} \leftarrow i + 1
$$

OUR PROTOCOL. Invariants: I1 (unique tickets) each i in 0..N-1 is claimed exactly once and claims are totally ordered by the modification order of next; I2 (ordered commit) committed = j implies results 0..j-1 have been appended exactly once in increasing order; I3 (bounded window) 0 <= next - committed <= K. I2 is proved by induction: the only transition j to j+1 is commit(j), whose guard is committed = j and which only the unique holder of ticket j executes. Progress: the holder of ticket committed is never blocked, and all waits are on smaller sequence numbers, so there is no cyclic wait. This is the ticket lock's now_serving counter, the Disruptor's cursor loop and the reorder buffer's head pointer applied to blocks.

Sources: mellorcrummey1991scalable, thompson2011disruptor, smith1988precise, cppreference_memory_order

## Open questions

- Does a 16 KB block actually outperform L2-sized blocks (for example 64 KB to 256 KB) for programmersRAG's real per-block work? The literature is split (Intel Rule 8 versus the morsel and X100 results), and the answer depends on how many passes touch each block and on how much of the time is computation rather than memory access. Only a block-size sweep on the target machine can settle it.
- What is the true working set per block once parsing structures, token buffers, hash tables, embedding/quantisation scratch and the stack are included? If it exceeds 32 KB (E-core) or about 24 KB (P-core logical CPU with a busy SMT sibling) the L1 residency argument fails even though the input block is 16 KB.
- What is the measured relative throughput of E-cores versus P-cores, and the SMT yield of P-cores, for this workload on the i9-12950HX? The 0.6 figure comes from one 2026 preprint on HPC benchmarks and should not be assumed; P_eff in the speed-up model must be measured.
- How often does the Windows 11 scheduler (with Intel Thread Director) migrate a worker between cores or between core types in the middle of a block, and how much L1 warm-up is lost? User space cannot prevent this; whether CPU Sets reduce it without hurting throughput is untested here.
- How can L1d misses be measured on the owner's Windows machine? Hardware performance counters normally require a profiler or driver (for example VTune or Windows Performance Recorder) and administrative rights; if unavailable, the paper can only report timing curves versus block size as indirect evidence.
- Is the embedding model inference itself (the dominant cost in most RAG indexers) inside the 16 KB-per-thread stage? Model weights are hundreds of megabytes and cannot be L1-resident, so the L1 argument applies only to the pre- and post-processing and to int8 scoring kernels, and the GPU or llama.cpp stage may dominate the serial fraction.
- What token window K and what waiting strategy (spin with PAUSE, atomic wait, or the draining variant) give the best throughput on a hybrid CPU where a slow E-core may hold the lowest uncommitted sequence number and stall the commit cursor (head-of-line blocking)?
- Should the stronger start-gate variant (serialised prologue per block) be implemented at all? It makes the 'A before B' property observable at the first touch of the data, but adds serial time and FIFO-lock sensitivity to pre-emption; the owner needs to decide which observable event defines 'reaching the CPU'.
- Does MSVC 14.51 define std::hardware_destructive_interference_size as 64 on x64, and does the 64-set geometry derived here match what CPUID leaf 4 / GetLogicalProcessorInformationEx report on the actual machine? Neither was verified in this stage.
- Coverage gaps: the web-search budget for the session ran out, so the 2024-2026 literature scan is incomplete (no peer-reviewed 2024-2026 paper on L1-sized task granularity or on ordered parallel pipelines was found). Sources that could not be opened and were therefore not cited include Lee et al., 'On-the-Fly Pipeline Parallelism' (SPAA 2013 / TOPC 2015), the full text of Frigo et al. 1999, the ACM pages for several classics, and the Intel Intrinsics Guide entry for _mm256_dpbusd_avx_epi32.
