## Recommendations

- EMBEDDING MODEL (single recommendation): Qwen3-Embedding-0.6B, GGUF from Qwen/Qwen3-Embedding-0.6B-GGUF (Q8_0 639 MB for CPU, or f16 1198 MB), run in-process through llama.cpp with pooling type LAST. Dimension 1024 (MRL allows 32-1024; keep 1024). Nominal context 32K tokens but configure n_ctx to 2048-8192 because chunks are small and users report very high memory at 32K. Similarity: cosine on L2-normalised vectors. Licence: Apache-2.0.
- PROMPT FORMAT for the recommended model: query = 'Instruct: ' + one-sentence English task description + '\nQuery:' + user question; document = raw chunk text with no instruction. Append the literal '<|endoftext|>' token to every input unless a parity test proves the GGUF/llama.cpp build adds EOS itself. The task sentence is ours to choose (e.g. 'Given a question about a C codebase, retrieve the code chunks that answer it') and should be fixed and recorded in the paper because the model card reports 1-5% sensitivity to it.
- ADD A PARITY TEST to the C++ build: embed a fixed set of strings with and without the appended '<|endoftext|>' and assert the chosen path reproduces reference vectors (cosine > 0.999) from the model's reference implementation; this guards against the documented outdated-GGUF EOS and missing-pooling-metadata problems.
- ALTERNATES to A/B on the mimalloc query set, in this order: (a) jina-code-embeddings-0.5b GGUF (896-d, --pooling last, task prefixes) if and only if the project stays non-commercial, since it is CC-BY-NC-4.0; (b) EmbeddingGemma-300m QAT Q8_0 (768-d, 2K context, Gemma terms) as the fast small-footprint fallback; (c) watch-list only: voyage-4-nano (Apache-2.0) and pplx-embed-v1-0.6b (MIT), which score higher on MTEB Code in LightOn's 2026 table but have only unverified community GGUFs. Do not use nomic-embed-code (7B) on this hardware.
- VECTOR COMPRESSION (single recommendation): two-tier RaBitQ. Tier 1: centre on the corpus centroid, normalise, apply one fixed random orthogonal rotation, store the 1024 sign bits (128 bytes) plus two float32 side values per chunk; pack 120 vectors per 16 KB block and scan with AND/XOR + popcount against a 4-bit quantised rotated query. Tier 2: keep int8 (1 KB each, 16 per block) or float32 copies and rescore only shortlisted or near-threshold candidates. If a no-rescoring design is preferred, use extended RaBitQ at 4-5 bits per dimension (over 90-95% recall without re-ranking in the paper).
- USE THE ERROR BOUND IN THE PROBABILISTIC RETRIEVER: treat each 1-bit score as an interval of half-width about 0.045 (D = 1024); only candidates whose interval straddles the score equivalent to the 25% relevance probability need tier-2 rescoring. This gives the threshold-tracing feature a quantifiable, citable approximation error.
- DO NOT use product quantisation for this corpus: it needs k-means codebooks trained on far more vectors than a roughly 10^3-chunk repository provides and has no error bound. Do not MRL-truncate below 512 dimensions: the only published code-retrieval truncation curve loses about 2 points at 256-d and about 6 at 128-d, and retrieval is the task family most sensitive to compression; at this corpus size memory is not the constraint.
- GEOMETRY PREPROCESSING BEFORE KDE: subtract the corpus mean (the same centroid used by RaBitQ), optionally remove the top about d/100 principal components, re-normalise, and use a von Mises-Fisher / Gaussian kernel on the unit sphere. Report anisotropy (mean pairwise cosine) and hubness (skewness of N_10) before and after, since raw LLM embeddings are anisotropic and hub-prone and both effects bias density estimates toward the centroid.
- CHUNKING: implement cAST-style split-then-merge over a tree-sitter C parse with a budget of about 2,000 non-whitespace characters, keeping module-level code (macros, typedefs, static inline helpers, globals) rather than extracting function bodies only, and guaranteeing that concatenated chunks reproduce each file byte-for-byte (this also gives the inline-edit component exact byte offsets). Attach enclosing-function names as metadata so function-level grouping remains possible. Include fixed-size sliding windows as a baseline in the paper because the latest controlled study finds them competitive.
- EVALUATION FOR THE PAPER: report nDCG@10 and Recall@k on a hand-labelled mimalloc query set for float32, int8 and 1-bit(+rescore) variants, with retention expressed as a percentage of float32, and state clearly that public benchmarks (CoIR, MTEB Code, CodeSearchNet) contain little or no C and show 1-2 point evaluator-dependent variance. Include natural-language-sentence queries as well as short keyword queries, since the latter are reported to collapse all embedding models.
- SCOPE THE CACHE CLAIM HONESTLY: the 16 KB-per-thread L1 argument applies to the vector scan, KDE evaluation and rescoring stages. Transformer inference inside llama.cpp (hundreds of MB of weights) cannot be L1-resident, so embedding generation should be described as an offline/indexing cost and one query embedding per request.
- REFERENCE IMPLEMENTATION: the Apache-2.0 C++17 RaBitQ Library (VectorDB-NTU) builds on Windows x86-64 with AVX2 and can be used either as a dependency or as the oracle against which a minimal in-house 1-bit kernel is unit-tested. - [recent] Qwen3-Embedding-0.6B is a 0.6B-parameter, 28-layer decoder-only (causal attention) embedding model with 32K sequence length, 1024-d output, MRL support (user-defined output dimension 32-1024) and instruction awareness; the embedding is the last-layer hidden state of an appended [EOS] token (input format '{Instruction} {Query}<|endoftext|>'), similarity is cosine, and it is released under Apache-2.0.  (zhang2025qwen3, qwen3card2025)
- [recent] Qwen3 model card usage: queries are formatted as 'Instruct: {task_description}\nQuery:{query}', documents get no instruction, tokenizer padding_side should be 'left', embeddings are L2-normalised; the authors report that omitting the query instruction costs roughly 1-5% retrieval performance and advise writing instructions in English.  (qwen3card2025)
- [contested] Reported MTEB(Code, v1) nDCG@10 for Qwen3-Embedding-0.6B differs by evaluator: 75.41 (authors' paper, Table 3/9), 75.42 (MTEB leaderboard as copied by C2LLM, 2025-12-25), 74.69 (Jina's 'MTEB Code AVG' re-evaluation), 73.75 (LightOn's July 2026 re-evaluation). All open-source dense models were evaluated with input length 512.  (li2025coir)

- [recent] An independent large-scale code-to-code study (WISE 2026) that includes C++ finds Qwen3 Embedding and CodeXEmbed leading on quality (C++ CodeNet 99-100%, xCodeEval 98% for Qwen), CodeRankEmbed far behind on C++ (33% on CodeNet), and states that Qwen3-Embedder-600M 'consistently dominates' the precision-throughput trade-off, its 1024-d output giving faster distance computation and smaller indexes.  (venuta2026recall)
- [recent] CoREB (2026) reports that short keyword-style queries, the format closest to real developer search, collapse every evaluated embedding model to near-zero nDCG@10, that code-specialised embeddings give about 2x over general encoders on code-to-code, and that existing code benchmarks suffer from contamination and label noise.  (xue2026coreb)
- [established] Matryoshka Representation Learning trains one d-dimensional vector so that each prefix z_{1:m}, m in a set M of O(log d) sizes, is itself a usable representation, by summing the task loss over the nested sizes (weights c_m = 1); it adds no inference cost and reports up to 14x smaller embeddings at equal ImageNet-1K accuracy.  (kusupati2022matryoshka)
- [recent] Measured MRL truncation cost on code retrieval (EmbeddingGemma, MTEB(Code, v1)): 768-d 68.76, 512-d 68.48, 256-d 66.74, 128-d 62.96, i.e. about -0.3, -2.0 and -5.8 points. Independent 2026 work finds retrieval is the MTEB task family most sensitive to embedding compression, with degradation already visible at 1024 dims for a 3584-d model.  (embeddinggemmacard2025, kisako2026compression)
- [established] Post-hoc embedding quantisation (MTEB retrieval, mxbai-embed-large-v1, 1024-d): binary (1 bit/dim, 32x smaller) retains 92.53% without rescoring and 96.45% when the binary shortlist is rescored with the float32 query; int8 scalar quantisation (4x smaller, per-dimension min/max from a calibration set) retains about 99% to 99.3% with rescoring multiplier 4-5. Measured exact-search CPU speedups averaged 3.66x (int8) and 24.76x (binary).  (shakir2024quantization)
- [contested] Calibrated int8 is not uniformly safe: a 2025 MTEB study measured a 1.5-3.5% drop for int8 without rescoring (model dependent) and found float8 casting loses <0.3% at the same 4x compression without needing calibration data; PCA was the best dimensionality reduction and PCA-50% + float8 gave 8x compression with less loss than int8 alone.  (huerga2025storage)
- [recent] Quantisation-aware embedding models are a 2026 trend: pplx-embed trains with int8 tanh quantisation from the start (straight-through estimator) and outputs int8 natively; its 0.6B/1024-d model loses roughly 2-4.4 points under binary quantisation while the 4B/2560-d model loses at most 1.6, which the authors attribute partly to output dimension. voyage-4-nano likewise uses quantisation-aware training for int8 and binary outputs.  (eslami2026pplx, voyage4nano2026)
- [established] Product quantisation splits a vector into m sub-vectors, quantises each with a k*-centroid k-means codebook (code length m log2 k*, typically m=8, k*=256 for 64-bit codes) and estimates distances asymmetrically from per-subquantiser lookup tables; it has no theoretical error bound, and at 32x or higher compression PQ-type methods give poor recall (<80%) unless raw vectors are re-ranked; at 4 or more bits per dimension PQ/OPQ usually fail to beat plain scalar quantisation.  (jegou2011pq, gao2025exrabitq, gao2024rabitq, douze2024faiss)
- [recent] RaBitQ (SIGMOD 2024) quantises a centred, normalised D-dimensional vector to a D-bit string (signs of the inversely rotated vector P^{-1}o), and estimates the inner product with <o_bar,q>/<o_bar,o>, which is unbiased with error O(1/sqrt(D)) with high probability, asymptotically optimal for D-bit codes; <o_bar,o> concentrates around 0.8; the query is scalar-quantised to B_q = 4 bits so the estimate reduces to B_q bitwise-AND plus popcount operations over D-bit strings; the bound is additive and holds regardless of data distribution.  (gao2024rabitq)
- [recent] Extended RaBitQ (published in Proc. ACM Manag. Data / SIGMOD 2025, DOI 10.1145/3725413) generalises to B bits per dimension with asymptotically optimal space-error trade-off; empirically 4, 5 and 7 bits per dimension give over 90%, 95% and 99% recall without re-ranking on all tested datasets (3 bits suffice for >95% on OpenAI embedding datasets), and the absolute inner-product error obeys epsilon < 2^{-B} * 5.75 / sqrt(D) with >99.9% probability.  (gao2025exrabitq, rabitqlib2026)
- [recent] A maintained Apache-2.0 C++17 implementation (RaBitQ Library, with 1-bit and multi-bit quantisation, IVF, HNSW; AVX2/FMA with optional AVX-512; Windows x86-64 source builds validated) exists and can serve as a reference for the C++ rewrite.  (rabitqlib2026)
- [contested] The superiority claims of the competing TurboQuant method are disputed: a 2026 technical note by the RaBitQ authors reports TurboQuant performing worse than RaBitQ in most tested inner-product, nearest-neighbour and KV-cache settings and that several TurboQuant runtime and recall results could not be reproduced. (Only the RaBitQ authors' side was read for this dossier.)  (gao2026revisiting)
- [established] Anisotropy: contextual transformer representations occupy a narrow cone. If representations were isotropic the mean cosine similarity of random pairs would be 0; in GPT-2's last layer random word pairs have almost perfect cosine similarity. The degeneration was first attributed to likelihood training with weight tying, but anisotropy is also observed for other objectives and modalities, suggesting it is inherent to Transformer self-attention; a 2026 study links it to training dynamics that amplify tangent directions.  (ethayarajh2019contextual, gao2019degeneration, godey2024anisotropy, bernas2026anisotropy)
- [established] Post-hoc isotropy fixes are cheap linear operations: 'all-but-the-top' subtracts the mean and removes the top D (about d/100) principal components; whitening improves isotropy and also reduces dimensionality. Embedding trainers now regularise for it directly: EmbeddingGemma adds a spread-out (global orthogonal) regulariser so that random pairs behave like uniform samples on the sphere, explicitly to make embeddings robust to quantisation and efficient for ANN search.  (mu2018allbutthetop, su2021whitening, vera2025embeddinggemma)
- [established] Hubness: in high dimensions the distribution of k-occurrences N_k (how often a point is among the k nearest neighbours of others) becomes strongly right-skewed, producing hubs; points closer to the data mean tend to become hubs; it is an inherent property of high-dimensional data distributions. Centering the data at its centroid provably and empirically reduces hubs for inner-product/cosine similarity.  (radovanovic2010hubs, suzuki2013centering)
- [recent] Hubness is an active RAG concern in 2026: a few hub vectors can be retrieved for many unrelated queries (a poisoning vector); an admission-time global gate detects hub-like documents, and a per-topic gate adds nothing, which the authors explain by anisotropy coupling local and global visibility (tested on five encoders, 384-1024 dims, 100k-document corpora).  (pathak2026hubness)
- [established] Contrastive (InfoNCE) training asymptotically optimises alignment of positive pairs and uniformity on the hypersphere; the uniformity loss is the log of the mean pairwise Gaussian (RBF) potential, and the negative-sample term of the contrastive loss can be read as a resubstitution entropy estimator using a von Mises-Fisher kernel density estimate. Hence KDE on the unit sphere with a vMF/Gaussian kernel is the density estimator that matches how these embedding models were trained.  (wang2020alignment)
- [recent] cAST (Findings of EMNLP 2025) chunks code by parsing with tree-sitter, recursively splitting AST nodes that exceed a budget and greedily merging adjacent sibling nodes, measuring size in non-whitespace characters and guaranteeing that concatenated chunks reproduce the file verbatim; versus fixed-size line chunking it reports +4.3 Recall@5 on RepoEval retrieval and +2.67 Pass@1 on SWE-bench generation.  (zhang2025cast)
- [contested] The benefit of structure-aware chunking is contested: a controlled 2026 study (864 settings, 4 retrievers, 5 generators, RepoEval and CrossCodeEval, both Python) finds pure function-level chunking is the worst strategy (3.57-5.64 points lower Exact Match on RepoEval, never Pareto-optimal) because functions are shorter than the budget and module-level code outside function bodies is discarded; cAST, declaration and sliding-window chunking perform comparably with sliding window narrowly ahead; chunk size has a weak non-monotonic effect (<=1.9 pp) while total retrieved context length dominates (up to 4.2 pp); recommended default chunk size 2,000 non-whitespace characters and context >= 4,096 tokens.  (wu2026chunking, zhang2025cast)
- [contested] Pooling choice is contested across 2025 model papers: Jina's ablation finds last-token pooling beats mean and latent-attention pooling on a causal code backbone; C2LLM argues EOS pooling is an information bottleneck for long code and replaces it with cross-attention (PMA) pooling; EmbeddingGemma finds mean pooling beats attention pooling for a bidirectional encoder. The pooling must therefore be taken from the chosen model's card, not chosen freely.  (kryvosheieva2025jina, qin2025c2llm, vera2025embeddinggemma)
- [our_proposal] PROPOSAL (model): use Qwen3-Embedding-0.6B via llama.cpp (GGUF Q8_0 or f16, LLAMA_POOLING_TYPE_LAST, 1024-d, L2-normalised, cosine) as the primary embedder. Rationale: only candidate that combines a permissive licence (Apache-2.0), an official GGUF, a pooling type llama.cpp supports natively, MTEB Code of about 74-75, the best sub-1B result on the repository-level CORE-Bench, and independent C++ code-to-code evidence. jina-code-embeddings-0.5b scores about 4 points higher on MTEB Code but is CC-BY-NC; EmbeddingGemma is 6-7 points lower with a 2K context.  (zhang2025qwen3, qwen3card2025, qwen3gguf2025, kryvosheieva2025jina, jinagguf2025, embeddinggemmacard2025, zhang2026corebench, venuta2026recall, sourty2026denseon, llamacpp2026)
- [our_proposal] PROPOSAL (compression, derived arithmetic): with D=1024, a 1-bit RaBitQ code is 128 bytes; adding two float32 side values (distance to centroid and <o_bar,o>) gives 136 bytes, so one 16 KB block holds floor(16384/136) = 120 vectors (16,320 bytes). The per-thread working set is one 16 KB code block plus a 4-bit quantised query (4 x 128 = 512 bytes) or a 4 KB float query, i.e. about 17-21 KB, which fits in both the 48 KB P-core and 32 KB E-core L1d. For comparison a 16 KB block holds only 16 int8 vectors or 4 float32 vectors at 1024-d, and 31 vectors with 4-bit extended RaBitQ (520 bytes each).  (gao2024rabitq, gao2025exrabitq, shakir2024quantization)
- [our_proposal] PROPOSAL (error budget, derived): plugging D=1024, <o_bar,o>=0.8 and epsilon_0=1.9 into RaBitQ's bound gives a cosine-estimate half-width of sqrt(0.36/0.64)*1.9/sqrt(1023) = 0.0446; the extended-RaBitQ empirical formula gives 0.0898 (B=1), 0.0449 (B=2), 0.0112 (B=4) and 0.0007 (B=8) at >99.9% confidence. Therefore a 1-bit scan is adequate for shortlisting, but any candidate whose estimated score lies within the bound of the relevance threshold must be rescored with int8 or float32 vectors before the 25%-probability cut is applied.  (gao2024rabitq, gao2025exrabitq)
- [our_proposal] PROPOSAL (geometry for KDE): RaBitQ's mandatory normalisation o=(o_r-c)/||o_r-c|| is a centering step, and centering is also the classical remedy for hubness and removes the common-direction component responsible for anisotropy; so one corpus centroid c should be computed once and used for (i) RaBitQ codes, (ii) hub reduction and (iii) the vectors fed to the vMF/Gaussian KDE. Mean pairwise cosine (anisotropy) and k-occurrence skewness S_{N_10} (hubness) should be reported before and after centering on the mimalloc corpus.  (gao2024rabitq, suzuki2013centering, radovanovic2010hubs, ethayarajh2019contextual, mu2018allbutthetop, wang2020alignment)
- [our_proposal] PROPOSAL (PQ is a poor fit here): a mimalloc-sized corpus yields only on the order of 10^3 chunk vectors, too few to train 256-centroid k-means codebooks per sub-space reliably, and PQ offers no error bound with which to decide which candidates near the probability threshold need rescoring; RaBitQ needs no training beyond one centroid and one random rotation.  (jegou2011pq, gao2024rabitq, gao2025exrabitq)

## Formulas

### Qwen3-Embedding training loss (masked InfoNCE)

$$
L_{\mathrm{embedding}}=-\frac{1}{N}\sum_{i}^{N}\log\frac{e^{s(q_i,d_i^{+})/\tau}}{Z_i},\qquad Z_i=e^{s(q_i,d_i^{+})/\tau}+\sum_{k}^{K}m_{ik}e^{s(q_i,d_{i,k}^{-})/\tau}+\sum_{j\neq i}m_{ij}e^{s(q_i,q_j)/\tau}+\sum_{j\neq i}m_{ij}e^{s(d_i^{+},d_j)/\tau}+\sum_{j\neq i}m_{ij}e^{s(q_i,d_j)/\tau},\qquad m_{ij}=\begin{cases}0&\text{if } s_{ij}>s(q_i,d_i^{+})+0.1\ \text{or}\ d_j=d_i^{+}\\1&\text{otherwise}\end{cases}
$$

Copied from Section 3 of the Qwen3 Embedding paper. s is cosine similarity, tau the temperature, K the number of hard negatives; the mask m_ij removes likely false negatives (in-batch items scoring more than 0.1 above the positive). This is the objective that shapes the geometry of the recommended model's embedding space.

Sources: zhang2025qwen3

### Jina code embeddings InfoNCE loss

$$
\mathcal{L}_{\mathrm{NCE}}(S(B),\tau):=-\sum_{i,j=0}^{n}\ln\sigma(S(B),\tau,i,j),\qquad \sigma(S,\tau,i,j):=\frac{e^{S_{i,j}/\tau}}{\sum_{k=0}^{n}e^{S_{i,k}/\tau}}
$$

Reproduced as printed in the paper (Section 4); S(B) is the matrix of cosine similarities of the batch, tau = 0.05, batch size n = 512 for the 0.5B model and 256 for the 1.5B model, sequence length 512. The paper states that pairs (q_i, d_i) are treated as similar and all (q_i, d_j), i != j, as dissimilar.

Sources: kryvosheieva2025jina

### Matryoshka Representation Learning objective

$$
\min_{\{\mathbf{W}^{(m)}\}_{m\in\mathcal{M}},\ \theta_F}\ \frac{1}{N}\sum_{i\in[N]}\sum_{m\in\mathcal{M}}c_m\cdot\mathcal{L}\left(\mathbf{W}^{(m)}\cdot F(x_i;\theta_F)_{1:m}\ ;\ y_i\right)
$$

Equation 1 of Kusupati et al. M is the set of nested sizes with |M| <= floor(log d) (e.g. {8,16,...,2048}), F(x)_{1:m} is the first m coordinates, c_m = 1 in the paper. Embedding models apply the same nesting to their contrastive loss (EmbeddingGemma: 768/512/256/128; LightOn: 128/256/512/768).

Sources: kusupati2022matryoshka, vera2025embeddinggemma, sourty2026denseon

### MRL truncation at inference

$$
\tilde{z}^{(m)}=\frac{z_{1:m}}{\lVert z_{1:m}\rVert_2}
$$

Notation ours; the operation is stated in words in the EmbeddingGemma card ('truncate the output embedding of size 768 to their desired size and then re-normalize'). With llama.cpp the slice is done client-side: the Jina GGUF card notes llama.cpp always returns the full-size vector.

Sources: embeddinggemmacard2025, jinagguf2025, kusupati2022matryoshka

### RaBitQ normalisation and distance decomposition

$$
\mathbf{o}:=\frac{\mathbf{o}_r-\mathbf{c}}{\|\mathbf{o}_r-\mathbf{c}\|},\quad \mathbf{q}:=\frac{\mathbf{q}_r-\mathbf{c}}{\|\mathbf{q}_r-\mathbf{c}\|},\qquad \|\mathbf{o}_r-\mathbf{q}_r\|^{2}=\|\mathbf{o}_r-\mathbf{c}\|^{2}+\|\mathbf{q}_r-\mathbf{c}\|^{2}-2\,\|\mathbf{o}_r-\mathbf{c}\|\,\|\mathbf{q}_r-\mathbf{c}\|\,\langle\mathbf{q},\mathbf{o}\rangle
$$

Raw data vector o_r and query q_r are centred on a centroid c and normalised; the distance then depends only on two norms (one precomputed per vector, one per query) and the inner product of unit vectors, which is what the code estimates.

Sources: gao2024rabitq

### RaBitQ codebook and 1-bit code

$$
\mathcal{C}:=\left\{+\tfrac{1}{\sqrt{D}},-\tfrac{1}{\sqrt{D}}\right\}^{D},\qquad \bar{\mathbf{x}}=\arg\max_{\mathbf{x}\in\mathcal{C}}\langle P^{-1}\mathbf{o},\mathbf{x}\rangle,\qquad \bar{\mathbf{x}}=\frac{2\bar{\mathbf{x}}_b-\mathbf{1}_D}{\sqrt{D}},\qquad \bar{\mathbf{o}}:=P\bar{\mathbf{x}}
$$

P is a random orthogonal matrix. The code x_b in {0,1}^D is simply the sign pattern of P^{-1} o, so encoding is one rotation plus D sign tests; for D = 1024 the code is 128 bytes.

Sources: gao2024rabitq

### RaBitQ unbiased estimator and error bound

$$
\mathbb{E}\left[\frac{\langle\bar{\mathbf{o}},\mathbf{q}\rangle}{\langle\bar{\mathbf{o}},\mathbf{o}\rangle}\right]=\langle\mathbf{o},\mathbf{q}\rangle,\qquad \mathbb{P}\left\{\left|\frac{\langle\bar{\mathbf{o}},\mathbf{q}\rangle}{\langle\bar{\mathbf{o}},\mathbf{o}\rangle}-\langle\mathbf{o},\mathbf{q}\rangle\right|>\sqrt{\frac{1-\langle\bar{\mathbf{o}},\mathbf{o}\rangle^{2}}{\langle\bar{\mathbf{o}},\mathbf{o}\rangle^{2}}}\cdot\frac{\epsilon_0}{\sqrt{D-1}}\right\}\le 2e^{-c_0\epsilon_0^{2}}
$$

Theorem 3.2 (Eqs. 13-14). <o_bar,o> is precomputed per vector and concentrates around 0.8; epsilon_0 is fixed to 1.9 in practice; the bound is O(1/sqrt(D)), which is optimal for D-bit codes (Alon and Klartag 2017, as cited by the paper). <o_bar,q> equals <x_bar,q'> with q' = P^{-1} q and is computed with B_q = 4 bit-planes of AND + popcount.

Sources: gao2024rabitq

### Extended RaBitQ bits-per-dimension requirement and empirical error formula

$$
B=\Theta\left(\log\left(\frac{1}{D}\cdot\frac{1}{\epsilon^{2}}\log\frac{1}{\delta}\right)\right),\qquad \epsilon<2^{-B}\cdot\frac{c_\epsilon}{\sqrt{D}},\quad c_\epsilon=5.75\ \ (\text{with}>99.9\%\text{ probability})
$$

Theorem 3.2 and the 'Empirical Formula' remark of the extended RaBitQ paper: error decays exponentially in the number of bits per dimension B. The constant 5.75 is measured experimentally by the authors, not derived.

Sources: gao2025exrabitq

### Product quantisation: code length and asymmetric distance (ADC)

$$
\ell=m\log_2 k^{*},\qquad \tilde{d}(x,y)^{2}=d\big(x,q(y)\big)^{2}=\sum_{j=1}^{m}d\big(u_j(x),q_j(u_j(y))\big)^{2}
$$

From Jegou et al. (Eq. 13, written here in squared form): x is split into m sub-vectors u_j(x), each database sub-vector is replaced by its nearest of k* centroids, and the m x k* table of squared sub-distances is computed once per query. The paper states k* = 256 and m = 8 is often a reasonable choice (64-bit codes).

Sources: jegou2011pq

### Native int8 embedding quantisation (pplx-embed)

$$
\mathbf{e}=\left\lfloor 127\cdot\tanh\left(\frac{1}{L}\sum_{l=1}^{L}\mathbf{v}_l\right)+\frac{1}{2}\right\rfloor
$$

Section 2.2 of the pplx-embed paper: mean-pool the L token vectors, squash with tanh, scale to the int8 range and round; applied during training with a straight-through estimator. Binary quantisation sets each entry of the mean-pooled vector to -1 or +1. Shown as the calibration-free alternative to min/max int8.

Sources: eslami2026pplx

### Calibrated int8 scalar quantisation (our formalisation)

$$
q_i=\mathrm{clip}\left(\left\lfloor 255\cdot\frac{x_i-\min_i}{\max_i-\min_i}\right\rceil-128,\ -128,\ 127\right)
$$

OUR FORMALISATION of the procedure described in words by Shakir, Aarsen and Lee: per-dimension min_i and max_i are computed over a calibration set of embeddings, the range is divided into 256 buckets and each value is mapped to its bucket index in [-128,127]. Derivation: linear map of [min_i,max_i] onto [0,255], rounding, shift by 128, clipping for out-of-range values. The source gives no closed formula, so exact rounding conventions are our choice.

Sources: shakir2024quantization

### Alignment and uniformity losses (hypersphere geometry of contrastive embeddings)

$$
\mathcal{L}_{\mathrm{align}}(f;\alpha)=\mathbb{E}_{(x,y)\sim p_{\mathrm{pos}}}\left[\|f(x)-f(y)\|_2^{\alpha}\right],\qquad \mathcal{L}_{\mathrm{uniform}}(f;t)=\log\ \mathbb{E}_{x,y\,\overset{\mathrm{i.i.d.}}{\sim}\,p_{\mathrm{data}}}\left[e^{-t\|f(x)-f(y)\|_2^{2}}\right],\qquad G_t(u,v)=e^{-t\|u-v\|_2^{2}}=e^{2t\,u^{\top}v-2t}
$$

Wang and Isola; defaults alpha = 2, t = 2 in their reference code. G_t is the Gaussian potential (RBF) kernel on the sphere; on unit vectors it is a von Mises-Fisher kernel in u^T v with concentration 2t. L_uniform is therefore the log of a kernel density sum, the same quantity a KDE-based relevance model evaluates.

Sources: wang2020alignment

### EmbeddingGemma spread-out regulariser

$$
\mathcal{L}_S=\frac{1}{B(B-1)}\sum_{i,j\in\mathcal{B}:\,i\neq j}(\mathbf{q}_i^{\top}\mathbf{q}_j)^{2}+\frac{1}{B(B-1)}\sum_{i,j\in\mathcal{B}:\,i\neq j}(\mathbf{p}_i^{+\top}\mathbf{p}_j^{+})^{2}
$$

Equation 4 of the EmbeddingGemma paper (second-moment term of the global orthogonal regulariser): pushes random pairs of query and of passage embeddings toward the statistics of points sampled uniformly on the unit sphere, explicitly to improve robustness to embedding quantisation and ANN retrieval.

Sources: vera2025embeddinggemma

### All-but-the-top post-processing

$$
\mu=\frac{1}{|V|}\sum_{w\in V}v(w),\quad \tilde{v}(w)=v(w)-\mu,\quad u_1,\dots,u_d=\mathrm{PCA}(\{\tilde{v}(w)\}),\quad v'(w)=\tilde{v}(w)-\sum_{i=1}^{D}\big(u_i^{\top}v(w)\big)u_i
$$

Algorithm 1 of Mu, Bhat and Viswanath as printed; the only hyper-parameter D is recommended to be about d/100 (about 10 for d = 1024). Proposed here as optional preprocessing of chunk embeddings before density estimation.

Sources: mu2018allbutthetop

### Anisotropy as mean pairwise cosine (notation ours)

$$
A=\mathbb{E}_{i\neq j}\left[\frac{x_i^{\top}x_j}{\|x_i\|\,\|x_j\|}\right]
$$

Notation ours for the measure Ethayarajh describes in words: the average cosine similarity between uniformly randomly sampled representations; A = 0 for an isotropic space, A close to 1 for a narrow cone.

Sources: ethayarajh2019contextual

### Hubness: skewness of the k-occurrence distribution

$$
S_{N_k}=\frac{\mathbb{E}\left[(N_k-\mu_{N_k})^{3}\right]}{\sigma_{N_k}^{3}}
$$

Radovanovic et al., Section 3: N_k(x) is the number of times x appears among the k nearest neighbours of the other points; S = 0 means no skew, positive values mean a right tail of hubs. The paper fixes k = 10 in its tables.

Sources: radovanovic2010hubs

### Vectors per 16 KB cache block (our derivation)

$$
n_{\mathrm{blk}}=\left\lfloor\frac{16384}{\lceil D\,B/8\rceil+s}\right\rfloor
$$

OUR DERIVATION. D = dimension, B = bits per dimension, s = bytes of per-vector side information. Examples at D = 1024: B=1, s=8 (two float32: centroid distance and <o_bar,o>) gives 16384/136 -> 120 vectors; B=4, s=8 gives 16384/520 -> 31; int8 (B=8, s=0) gives 16; float32 (B=32, s=0) gives 4. With MRL truncation to D=256: 1-bit + 8 bytes gives 16384/40 -> 409, int8 gives 64.

Sources: gao2024rabitq, gao2025exrabitq

### Numerical error half-width at D = 1024 and threshold-aware rescoring rule (our derivation)

$$
\Delta_{1}=\sqrt{\frac{1-0.8^{2}}{0.8^{2}}}\cdot\frac{1.9}{\sqrt{1023}}\approx 0.0446,\qquad \Delta_{B}^{\mathrm{emp}}=\frac{5.75}{2^{B}\sqrt{1024}}\in\{0.0898,\,0.0449,\,0.0112,\,0.0007\}\ \text{for}\ B\in\{1,2,4,8\},\qquad \text{rescore } i \iff |\hat{s}_i-s_{\mathrm{thr}}|\le\Delta
$$

OUR DERIVATION. First expression substitutes D = 1024, <o_bar,o> = 0.8 and epsilon_0 = 1.9 into RaBitQ Eq. 14: sqrt(0.36/0.64) = 0.75; 0.75 x 1.9 = 1.425; 1.425/31.98 = 0.0446. Second substitutes D = 1024 into the extended-RaBitQ empirical formula. Third is the proposed rule: a candidate whose estimated cosine s_hat lies within Delta of the score s_thr corresponding to the 25% relevance probability is rescored with higher-precision vectors, mirroring RaBitQ's own use of the bound to decide re-ranking.

Sources: gao2024rabitq, gao2025exrabitq

## Open questions

- How well does Qwen3-Embedding-0.6B retrieve C allocator code specifically? CodeSearchNet has no C, CoIR/MTEB-Code are dominated by Python/Java/SQL/contest code, and the only C-family evidence found is C++ code-to-code retrieval (Venuta et al.). A mimalloc-specific labelled query set is needed; no published number transfers directly.
- What is the retrieval cost of GGUF weight quantisation (Q8_0 vs f16 vs 4-bit) for Qwen3-Embedding-0.6B? Only EmbeddingGemma publishes quantised-checkpoint scores (and those are quantisation-aware-trained); no equivalent table was found for Qwen3 or for post-hoc GGUF quantisation of any code embedder.
- What is the MRL truncation curve of Qwen3-Embedding-0.6B on code retrieval (1024 -> 512 -> 256)? The paper and card assert MRL support for 32-1024 dims but publish no per-dimension code scores; the only code truncation curve found is EmbeddingGemma's.
- Is the official Qwen3-Embedding-0.6B GGUF still affected by the EOS / pooling-metadata problem with the llama.cpp version that will be vendored? The evidence is user reports from 2025-06 to 2025-12; it must be re-tested rather than assumed either way.
- Does RaBitQ's relative accuracy hold for strongly anisotropic LLM embeddings of a tiny, single-repository corpus? The additive bound is distribution-free, but the authors note the multiplicative bound assumes well-normalised data and that they 'have yet to extensively explore the normalization step'. After centring a very homogeneous corpus, residual norms may be small and cosine gaps between relevant and irrelevant chunks may be comparable to the 0.045 error half-width.
- Can the dense 1024 x 1024 random rotation (4 MB as float32, not L1-resident) be replaced by a structured fast transform without losing the guarantee? Papers on randomized Hadamard transforms for quantisation appeared in search results in 2026 but were not opened, so no claim is made here.
- Which chunk granularity is best for C with heavy macro and header use? cAST and the controlled chunking study evaluate Python benchmarks only, and they disagree with the intuition that function-level units are optimal; the owner's 'similar functions' framing may need chunks plus function metadata rather than pure function chunks.
- What kernel bandwidth / vMF concentration should the KDE use? Wang and Isola link the contrastive denominator to a vMF KDE whose concentration is the inverse training temperature (tau = 0.05 is documented for Jina and C2LLM, but the Qwen3 paper text read here does not state its tau), so the bandwidth must be tuned empirically on the target corpus.
- Is hubness material at N of about 10^3 chunks? The hubness literature studies large or synthetic high-dimensional sets; the effect size on a single small repository is unmeasured and should be reported via S_{N_10} before claiming a benefit from centring.
- How trustworthy are MTEB-Code rankings given benchmark contamination and training-set overlap? C2LLM and LateOn explicitly train on the training splits of the MTEB-Code tasks, CoREB reports contamination and label noise in existing benchmarks, and the same model's score varies by 1.7 points across evaluators.
- The RaBitQ versus TurboQuant dispute was read from the RaBitQ authors' side only; the TurboQuant paper itself was not opened, so its claims are not represented here.
